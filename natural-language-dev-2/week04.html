対戦ゲームの仕組みを読み解こう

Week 4 木曜 3・4限
テーマ
前回、1人の学生がAIエージェントへの指示だけで実装した「6人同時対戦のリアルタイム対戦ゲーム」を教材に、その裏側の構造をクラス全体で図解しながら読み解き、実はすでに世界中からアクセスできる状態だったという事実と、そこに潜む脆弱性・セオリーとしての多層防御の考え方を理解する
キーワード
WebSocket / サーバーとルーム（部屋） / ポート転送の公開設定 / NAT（ネットワークアドレス変換） / 脆弱性 / 多層防御（Defense in Depth）
必要な準備
特になし。実装した本人はプロジェクトを開ける状態にしておくとよい

この回のゴール

  • 1人の学生が作った「6人同時対戦」が、裏側でどんな技術を使っていた可能性が高いかを図解で読み解く
  • サーバー役と、パスコードで区別されるルーム（部屋）の関係を理解する
  • 実は「学校WiFi内だけ」ではなく、すでに世界中からアクセスできる状態だったという事実を、公式ドキュメントで確認する
  • ポート転送を「公開」にすると何が起きるかを理解し、そこに潜む脆弱性と、セオリーとしての多層防御の考え方を知る
今日の位置づけ: 対戦ゲームを実装したのはクラスで1人だけです。今日はその1人の体験を教材に、「AIエージェントがこの種の機能を実装するときに、一般的にどんな技術を使うか」を、実装した本人の説明や図解を通じてクラス全体で理解することが目的です。断定できない部分は「〜という技術が使われていた可能性が高い」という形で扱います。

「なぜ動いたのか」を考える

  • 作った本人が「部屋」を作り、他の人がそのパスコードを入力して参加する仕組みだったことを思い出す

疑問を持つ

  • 仮説を立ててみる: 「1人が動かしたキャラクターが、どうやって他の5人の画面にも反映されたのか」

  • この種の「複数人がリアルタイムに情報をやり取りする」機能を、AIコーディングエージェントが実装する際によく使う技術としてWebSocketを紹介する——サーバーとブラウザが接続したままになり、双方向にデータを送り合える仕組み（公式: WebSocket - Web APIs）

サーバー役は、実装した本人が動かしていたGitHub Codespaces上のプログラム——1つのサーバー役がプレイヤーの1人（作った本人自身）も兼ねていたと考えられる。全員が同じパスコードを入力して、同じ部屋（サーバー役）につながっていた

サーバーの役割を理解する

  • この図を見ながら、サーバー役が全員の操作（キャラクターの移動・攻撃等）をいったん受け取り、それを全員に配り直す——「ハブ」のような役割を果たしていたと考えられることを確認する
  • 自分の操作が他の人の画面に反映されるまでの流れ: 「自分の操作 → サーバー → 他の全員」という経路をたどっていたと考えられる

「部屋（ルーム）」の意味を考える

  • 同じサーバーの中に複数の対戦グループが同時に存在できるよう、パスコードで「今どの対戦グループに参加しているか」を区別する仕組みが「部屋（ルーム）」だったと考えられる

考えてみる: サーバー役がいなくなったら？

  • 図の中央（サーバー役）が消えたら、まわりの6つの箱はどうなるかを図を指さしながら話し合う——サーバーが1つに集中している構造では、それが止まると全員が影響を受けるという弱点に気づく

実は、もう世界中に公開されていた

問いかける

  • 「もし、学校の外にいる誰かが今日使ったURLとパスコードを知っていたら、参加できたと思いますか？」

事実を確認する

  • あのゲームのサーバー役は、実装した本人のGitHub Codespaces上で動いていた。Codespacesでは、ポート転送を「パブリック」に設定すると、それだけで学校WiFiの中かどうかに関係なくアクセスできる状態になる
  • 公式ドキュメントで確認: 「After you make a port public, anyone who knows the URL and port number can view the running application without needing to authenticate.」（公式: Forwarding ports in your codespace）。別ページにも同様の記載: 「Publicly forwarded ports: Are accessible on the internet, and anyone on the internet can access them. No authentication is needed to access public forwarded ports.」（公式: Security in GitHub Codespaces）
  • つまり——「学校WiFi内でしか動かなかった」というのは、実は起きていなかった。技術的には、URLとポート番号さえ知っていればGitHubアカウントなしで、家からでも海外からでも、その瞬間からアクセスできる状態だった

パブリックに設定した瞬間、技術的には学校の外・海外からでもアクセスできる状態になっていた。実際に参加したのは学校WiFi内の6人だけだったが、それは「ネットワークで区切られていたから」ではなく、「URLを知っていたのがその6人だけだったから」だったと考えられる

なぜ、これが特別なことなのか

  • ふつうの家庭用・学校用のルーターの内側にあるパソコンは、NAT（Network Address Translation、ネットワークアドレス変換）という仕組みによって外部から直接アクセスできない（解説: What is NAT (Network Address Translation)?、Fortinet）——普段インターネットの「外側」から「内側」の1台のパソコンにいきなりアクセスされないのは、この仕組みのおかげ
  • GitHub Codespacesのポート転送は、この壁の外側まで届く橋（プロキシ）をあらかじめ用意している。だからこそ「パブリック」に切り替えるだけで、NATの壁を意識することなく、一気に世界中からアクセスできる状態になる
実際に確認してみる（2026-09-24実機確認）: Codespacesのパブリック転送URLに初めてブラウザでアクセスすると、GitHubが警告画面を挟む——「You are about to access a development port served by someone's codespace」という見出しのもと、「自分が信頼できる相手から送られたリンクのときだけ進んでください」「入力したクレジットカード番号やパスワード等の個人情報は、このサイトの開発者から見える可能性があります」という2つの注意書きと、「この警告はCodespaceのセッションごとに1回だけ表示されます」という説明、そしてContinueボタンが表示される。つまりGitHub自身もこのリスクを認識しているが、警告は「防御」ではなく「注意喚起」に過ぎず、ボタン1つで誰でも先に進めてしまう。しかも「セッションごとに1回だけ」なので、2回目以降は警告なしで直接アクセスできてしまう点にも注意。また、この警告が「個人情報は開発者から見える可能性がある」と述べている通り、危険は公開した側（自分たち）だけでなく、リンクを開く側（訪問者）にも及ぶ——知らない人から届いたCodespacesのリンクを不用意に開き、そこでパスワード等を入力するのも危険だということも合わせて理解しておく

だから、これは危険とも隣り合わせ

  • 「学校WiFiの中にいる人しか入れない」という、これまで無意識に頼っていたはずの制限は、そもそも存在していなかった。今回はたまたま誰にも気づかれなかっただけで、知らないうちに世界中に公開していたということになる——これがどれくらい危険なことなのかを、2限後半で詳しく見ていく

だから、多層防御というセオリーがある

どれくらい危険なことだったのか

  • 2限前半で確認した通り、あのゲームは「学校WiFiの中にいる人しか入れない」という制限には、実は最初から守られていなかった。残っていたのはパスコード（合言葉）だけという状態
  • WebSocketには、そもそも標準の認証の仕組みがない（OWASP: 「WebSockets don't have built-in authentication」）——「動いた」ことと「安全」であることは、まったく別の話だと理解する
  • パスコードは、画面共有・チャットの誤送信・肩越しに見られる等で漏れる可能性があり、サーバー側できちんと照合していなければ簡単に破られてしまう
  • 具体例: クラウド開発環境サービス「Gitpod」（Codespacesと同種のツール）で2023年、接続元（Origin）を確認していなかったために悪意のあるWebページを開かせるだけでWebSocket接続を乗っ取られ開発環境を乗っ取られる脆弱性（CVSS 9.6の重大な深刻度）が実際に見つかった（CVE-2023-0957 / Gitpod remote code execution 0-day vulnerability via WebSockets、Snyk Labs）。GitHub Codespaces自体にこの欠陥があるという話ではなく、同じ種類のツールで、認証・認可を怠るとどれくらい深刻な被害につながりうるかの実例として紹介する
  • 常時つながったままのWebSocket接続は、大量接続や大量メッセージによるサービス妨害（DoS）のリスクも高い（OWASP: 「Persistent WebSocket connections increase DoS risk」）

セオリー: 多層防御（Defense in Depth）という考え方

  • 本番で公開するリアルタイムアプリでは、「URLと合言葉」の1枚だけに頼らず、いくつもの層を重ねて守るのがセオリー（一次情報: WebSocket Security - OWASP Cheat Sheet Series）

  • 接続元の確認（Origin検証）: 接続してきた相手が想定しているWebページかどうかを毎回確認する。「許可リスト（allowlist）方式で、ワイルドカードや部分一致は避ける」のが原則（OWASP: 「Validate the Origin header on every handshake. Always use an explicit allowlist」）
  • 本人確認（認証）: クッキーだけに頼らず、トークン（合言葉より偽造・使い回しがしにくい鍵）で確認する方法が推奨されている（OWASP: 「use token-based authentication instead of relying solely on cookies」）
  • 権限の確認（認可）: 「入れるかどうか」を最初の1回だけでなく、操作のたびに確認する（OWASP: 「Check authorization for each action」）——「このパスコードで入った人が、この部屋のこの操作をしてよいか」を毎回問い直すイメージ
  • 頻度の制限（レート制限）: 1人あたりの接続数やメッセージの送信頻度に上限を設け、大量アクセスによる妨害を防ぐ（OWASP: メッセージサイズの上限と「rate limiting—100 messages per minute is a common starting point」）
今日作ったパスコード方式を否定する話ではありません: 教室内の短時間デモとしては現実的な妥協点です。ただし「公開する場面」「扱う情報の重要度」によって、どこまで防御を重ねるかを判断するのが設計者の仕事——というのが今日の一番のポイントです。

では、本番で正しく公開するには

  • Codespacesのポート転送は、あくまで開発中の一時的な動作確認のための機能。本番として正式に公開するなら、意図したセキュリティ設計を組み込めるクラウドサービス（Cloud Run等）にサーバーを置くのが筋——これが第7回で学ぶCloud Runにつながることを予告する

  • Cloud RunはWebSocket通信にも対応している（公式: Using WebSockets）。ただし接続時間には既定5分・最大60分の上限があり再接続が必要になること、複数のサーバーが同時に動く構成ではプレイヤー情報を共有する仕組み（Firestore等、第9回で学ぶ）が必要になることにも触れておく
