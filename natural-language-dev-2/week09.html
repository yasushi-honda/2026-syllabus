Cloudflare WorkersとD1に触れてみよう

Week 9 木曜 3・4限

📱 スマホで開く

テーマ
第7回で図だけ見た「ブラウザとDBの間のサーバー」を、Cloudflare Workersで実際に置く。D1（SQLのデータベース）を作り、スコアを保存・取得するWorkerを使用中のAIエージェントと作って、workers.devの公開URLに出す。無料の上限と、公開URLは誰でも開けることを確かめる
キーワード
Cloudflare Workers / D1 / Wrangler / wrangler login --device / バインディング（binding） / wrangler dev（ローカル） / --local と --remote / workers.dev / 無料の上限 / secret（合言葉）
必要な準備
自分が使うAIエージェント（Claude Code／Codex CLI／Antigravity CLI）が使える状態のCodespace。第8回の「指示の型カード」。Cloudflareのアカウントを、今日作ります（メールアドレスとパスワード。確認のメールを受け取れるアドレスを使います）。ログインの承認に使う、スマートフォンまたは別のブラウザ。

この回のゴール

  • Workers（サーバーの置き場所）とD1（データベース）が、それぞれ何をするものかを、図で説明できる
  • Codespaceからwrangler login --deviceでログインし、D1を作って、Workerに結びつける（バインディング）までの流れが言える
  • 第8回の4つの型で、AIエージェントにスコアの保存・取得ができるWorkerを作らせ、ローカルで確かめてから公開できる
  • 無料の上限（超えるとD1のクエリが失敗する）と、公開URLは誰でも開けること、そのための最低限の備え（合言葉、個人情報を入れない）を説明できる
今日の進め方: 授業計画を変更しました。これまでの予定にあった「Google Cloud」は、使わないことになりました（先生の決定）。かわりに、クレジットカードを使わず、無料の枠の中で試せるCloudflareを使います。Neon（第5〜7回）は、そのまま続けて使えます。今日は、NeonとD1の違いを、体験で比べるのが目的の1つです。コードは、AIエージェントに書かせます。人は、質問に答え、計画を読み、確かめ方を決めて、結果を自分の目で見ます。

授業の流れ

2コマ連続（90分 + 90分 = 計180分）。途中休憩あり。

1限 前半 約40分

授業計画の変更を知り、WorkersとD1の地図を見て、アカウントを作る

① なぜ変えたか（約5分）

  • 第7回で、ブラウザとDBの間にサーバーを置く理由を図で見た（置き場所の一つとして、Cloud Runを見た）。今日は、そのサーバーを、実際に置いて動かす。置き場所には、Cloudflare Workersを使う
  • これまでの予定の「Firestore」の回は、データベースを作って、保存・取得する体験が目的だった。同じ体験を、D1で行う

② 今日の地図（約10分）

  • D1は、公式の説明では、"Cloudflare's native serverless SQL database"（Cloudflareのサーバーレスな、SQLのデータベース）で、"D1 uses the familiar SQL query language (as used by SQLite)."（SQLiteと同じSQLを使う）。第6回で読んだSQLと、ほぼ同じ形で読める

③ 無料の枠と、超えたとき（約10分）

  • 公式の例では、5,000行の表にSELECT * FROM 表を実行すると、5,000行ぶん読んだと数えられる。「全部を一覧にする」を、むやみに何度も繰り返さない（今日の練習なら、まず上限に届くことはない）
  • D1の無料の上限を超えたときの動きは、公式の更新情報（2026-09-01）に、"D1 queries on the Workers Free plan will fail when an account exceeds the daily row read or row write limits."（無料プランでは、1日の行の読み書きの上限を超えると、D1のクエリが失敗する）、"Stored data is not affected."（保存したデータには影響しない）とある。上限は、世界標準時（UTC）の0時にリセットされる（日本時間の朝9時）

④ Cloudflareのアカウントを作る（約15分）

  • 公式の登録ページ（dash.cloudflare.com/sign-up/workers-and-pages）を開く。公式の手順では、メールアドレスとパスワードを入れる。登録後に、確認のメールが届くので、リンクを開いて確認する
  • クレジットカードなどの支払い方法を求められるかは、公式のドキュメントに明記が見つかっていません（先生が、授業前に登録の画面で確認します）。もし支払い方法の入力を求められたら、そこで止まって、手を挙げてください。入力して進めないこと。その場合は、1限後半の「ログインなしで進める方法」（下の注）を使います
  • パスワードは、他のサービスと使い回さない。パスワードも、あとで出てくるコードも、AIエージェントのチャットに貼らない（第5回の「パスワード相当の秘密」と同じ）
1限 後半 約50分

ログインし、型①②で計画を作り、D1を作る

① Codespaceからログインする（約15分）

  • Wrangler（ラングラー）は、Cloudflareが出しているコマンドの道具（CLI）。Workerの作成・公開と、D1の作成・操作に使う。第3回のghや、第6回のNeonのCLIと同じ種類の道具
  • ふつうのwrangler loginは、ブラウザがlocalhost:8976に戻ってくる作りで、Codespacesのような遠隔の環境では、つながらないことがある。公式（2026-08-04の更新情報）は、そうした環境のために--deviceを用意している。次を実行する:
npx wrangler login --device
  • 画面に、確認用のURLと、短いコードが出る。公式の例では、"To authorize Wrangler, please visit: https://dash.cloudflare.com/oauth2/device and enter the code:"。5分以内に、そのURLを開いてコードを入れ、承認する（スマートフォンで開いてもよい。公式にも、別のマシンから承認できるとある）。"Successfully logged in." が出れば成功
  • この方法は、Wrangler 4.119.0以降で使える（公式）。うまく動かないときは、npx wrangler@latest login --deviceのように、新しい版で試す。つまずいたら、手を挙げる
ログインなしで進める方法（支払い方法を求められたとき・ログインが通らないとき）: 公式には、ログインの前でも試せるwrangler deploy --temporaryがある（Wrangler 4.102.0以降）。"Claim within: 60 minutes" と出る一時的なアカウントにデプロイされ、60分以内に自分のアカウントとして引き受けない（claimしない）と、Cloudflareが、そのアカウントと中身を削除する、と公式に書かれている。公式の表では、一時アカウントでもD1は1つ・100MBまでとある。ただし、今日の手順のwrangler d1 createなどが、一時アカウントで通るかは、公式では確かめられていません（先生が試して、授業の前に結果を伝えます）。

② 型①②で、作るものを決める（約20分）

  • 今日のお題: 「名前とスコアを保存し、一覧を返す小さなAPI」（第4回の対戦ゲームの記録を、思い出して使ってよい）。自分の題材（第7回の最小版）に合わせて、保存する項目を1〜2個に変えてもよい（例: 名前・得点・メモ）
  • 空のフォルダを作り、エージェントを起動して、型①②の指示を送る（第8回の「指示の型カード」を開く）:
Cloudflare Workers と D1 で、「名前とスコアを保存して、一覧を返す」小さなAPIを作りたいです。
実行する前に、決めることを選択肢つきで質問してください（一度に3つまで、おすすめも添えて）。
私が選んだら、計画だけ出してください。まだ実行しないでください。
計画には、作るファイル、Wranglerで実行するコマンド、確かめ方を入れてください。
パスワードやAPIトークンは、私に貼らせないでください。
  • 出てきた計画を読んで、次の点を自分の目で確かめる: ①変えるファイルは、この新しいフォルダの中だけか（他の作業フォルダを触らない）②手順に、ローカルで確かめる段階があるか ③本番（remote）に反映する前に、止まって確認するか。足りなければ、言葉で直させる
  • エージェントが、プロジェクトの作り方を聞いてくることがある。公式のD1の手順では、npm create cloudflare@latestで、Hello World example・Worker only・TypeScriptを選び、Do you want to deploy your application?はNo（このあと変更を加えるため）としている。迷ったら、同じ選択でよい

③ D1を作る（約15分）

  • 計画のOKを出して、D1のデータベースを作るところまで進める。公式の例は次のとおり（名前は自由。ASCIIの英数字とハイフンで、32文字より短く）:
npx wrangler@latest d1 create scores-db
  • 途中で Would you like Wrangler to add it on your behalf? と聞かれたら、公式の手順どおりYesを選ぶ。これで、設定ファイルwrangler.jsoncに、バインディングが書き足される。エージェントに実行させたときも、この質問の答えは、人が見て決める
  • wrangler.jsoncの中身を、一度開いて読む。公式の形は次のとおり（database_idは、作ったときに出る固有の値）:
"d1_databases": [
  {
    "binding": "DB",
    "database_name": "scores-db",
    "database_id": "（作ったときに出る固有のID）"
  }
]
  • bindingの名前（上の例ではDB）が、Workerのコードの中でenv.DBとして使われる（公式: "Your binding is available in your Worker at env.<BINDING_NAME>"）。バインディングが、Neonでいう「接続文字列」のかわり。設定ファイルに書かれているのは、データベースの名前とIDで、パスワードのような秘密ではない（それでも、よく分からない値は、公開のリポジトリに出さない）
休憩 10分
2限 前半 約50分

型④確かめ方を渡して、ローカルで確かめ、本番に公開する

① Workerと表をつくらせる（約15分）

計画のとおり、次を作ってください。
1. 表を作る schema.sql（scores: id、名前、スコア、保存した日時。表がなければ作る形）
2. POST /scores で保存、GET /scores で一覧を返す Worker
   SQLは「?」と bind() を使って、入力をSQLに直接つなげないでください。
3. 作ったあと、変えたファイルと、実行したコマンドを教えてください。
まだ、本番（remote）には反映しないでください。
  • 公式のD1の手順の書き方は、次の形（読む練習用の例。エージェントが書いたコードが、これと同じ形になっているかを、見比べる）:
// 保存
await env.DB
  .prepare("INSERT INTO scores (name, score) VALUES (?, ?)")
  .bind(name, score)
  .run();

// 一覧
const { results } = await env.DB
  .prepare("SELECT * FROM scores ORDER BY id DESC LIMIT 20")
  .run();
return Response.json(results);
  • 公式では、"Using bind() prevents users from executing arbitrary SQL (known as "SQL injection") against your application and deleting or otherwise modifying your database."（bind()を使うと、入力を使って、勝手なSQLを実行され、データベースを消されたり書き換えられたりするのを防げる）と説明している。入力をSQLの文字列に直接つなげていないかを、必ず見る。LIMIT 20のように、返す件数を絞ると、上限の「行」も節約できる

② ローカルで確かめる（型④）（約20分）

  • wrangler devは、公式のとおりローカルモードが既定（"wrangler dev now uses local mode by default"）。ローカルのD1は、本番のデータとは別（公式: "A local session does not have access to your production data by default."）。だから、何度試しても本番に影響しない
  • D1のコマンドは、どちらに向けるかを必ず書く。ローカル用は--local、本番は--remote（公式: --local「Execute commands/files against a local DB for use with wrangler dev」、--remote「Execute commands/files against a remote D1 database」）。書き忘れると本番に向かう（公式: "Without the --local flag, the commands are executed against the remote version"）ので、今日は両方とも、毎回書く:
npx wrangler d1 execute scores-db --local --file=./schema.sql
npx wrangler dev
  • wrangler devは動き続けるので、2つ目のターミナルを開いて、確かめ方を実行する（公式の案内では、ローカルのアドレスはhttp://localhost:8787）。型④として、エージェントに次のように頼む:
ローカルで確かめてください。
1. POST /scores で、名前とスコアを2件保存する（curlのコマンドを教えてください）
2. GET /scores で、その2件が返るかを見る
実行したコマンドと、出力を、そのまま見せてください。
合わなければ、直して、もう一度確かめてください。
  • 見せてもらった出力が本当に2件になっているか、保存した名前とスコアが合っているかを、自分の目で読む。「できました」だけの返事は、確かめたことにならない
  • 確かめ方の失敗例も試す: 名前を空にして送る、スコアに文字を入れる。どんな返事になるかを見て、エージェントに「入力のチェックが足りないところは？」と聞く

③ 本番（remote）に反映して、公開する（約15分）

  • ローカルで確かめたら、本番のD1に表を作り、Workerを公開する。ここは公開に関わる操作なので、エージェントに「実行する前に、コマンドを見せて」と頼み、人がOKを出してから実行する:
npx wrangler d1 execute scores-db --remote --file=./schema.sql
npx wrangler deploy
  • 初めての公開では、Wranglerがworkers.devのサブドメインを決める画面を出すことがある（公式: "Wrangler will prompt you during the publish process to set one up."）。サブドメインはURLの一部になり、公開されるので、本名や学籍番号は使わない
  • 公開されたURL（名前.サブドメイン.workers.dev）に、curlでPOSTとGETをして、ローカルと同じ結果になるかを確かめる。初めての公開の直後は、つながらないことがある（公式: 523エラーが出たら、1分ほど待つ）。証拠として、実行したコマンドと出力を、メモに残す
2限 後半 約30分

公開URLの注意：誰でも開ける。合言葉と、入れないデータ

① 公開URLは、誰でも開ける（約5分）

  • 公式の説明に、"When enabled, your workers.dev URL is available publicly."（有効なとき、workers.devのURLは公開される）とある。つまり、URLを知った人は、誰でも、今日作ったAPIに送れる。第4回の「Codespacesのパブリックなポート」と同じ考え方で、認証は、自分でつけない限り、ない（公式は、Cloudflare Accessで訪問者に認証を求められる、とも書いている。今日は扱わない）
  • 確かめる: 隣の人に、自分のURLを伝え、GETだけしてもらう。一覧が見えることを確かめる。相手のURLに、POSTで書き込むのは、相手の許可を取ってから

② 書き込みに合言葉をつける（型①②④）（約15分）

  • エージェントに、型①②を使って頼む。合言葉の値は、人が自分で決めて、自分のターミナルで登録する（チャットに貼らない）:
POST /scores に、合言葉のチェックを足したいです。
実行する前に、方法を選択肢で質問し、計画だけ出してください。
・ヘッダーの合言葉が、secret の WRITE_PASS と違えば 401 を返す
・合言葉の値は、コードにも .env にも書かず、私が自分で登録します
・ローカルで確かめる方法（合言葉あり・なし）も、教えてください
まだ実行しないでください。
  • 登録のコマンドは、公式のとおりnpx wrangler secret put <KEY>（例: npx wrangler secret put WRITE_PASS）。実行すると、値を入力する画面になる。公式の注意: wrangler secret putは、新しい版を作って、すぐに公開する
  • ローカルで試す合言葉は、公式のとおり.dev.varsに書く。公式: "The .dev.vars and .env files should not be committed to git."（git に入れない）。.gitignoreに.dev.vars*が入っているかを、確かめる
  • 確かめ方（型④）: まずローカル（wrangler dev）で、合言葉なしでPOST → 401、合言葉ありでPOST → 保存、を、コマンドと出力で見せてもらう。合言葉の値は、画面に出さない
  • 公開側に反映する: wrangler secret putは、合言葉の値を公開側に登録するだけで、ローカルで直したコードは公開されない。直したコードは、もう一度npx wrangler deployで公開する。そのあと公開URLに、合言葉なしでPOST → 401が返ることを、コマンドと出力で確かめる（公開側が古いままだと、合言葉なしでも保存できてしまう）

見るところNeon（第5〜7回）D1（今日）

無料の上限第5〜6回の手順では、72時間で期限が切れる一時DB1日の行の読み書きの上限。超えると失敗する。データは残る
サーバー別に用意する（第7回の図）Workerが、その役目。公開URLは誰でも開ける
  • 隣の人と、1分ずつ話す。自分の進級制作（または第7回の題材）に使うなら、Neon・D1のどちらが合うか。その理由を、1つ。次回（設計）の材料になる
  • 型③の確認として、エージェントに「CloudflareのドキュメントをAIが読むためのMCPサーバーは、あるか」と聞いてみる（公式に、Cloudflare自身のMCPサーバーの一覧がある）。今日は、MCPサーバーを足しません
