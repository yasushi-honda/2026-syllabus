Spec-Driven Development入門

Week 6 木曜 1・2限
テーマ
Spec-Driven Development（SDD：仕様駆動開発）を、GitHub 公式の Spec Kit(specify CLI) で体験する。第5回までの PRD/ADR/Plan Mode を 「仕様が実行可能な成果物になる」方向へ一段進める
キーワード
SDD / Spec Kit / /speckit.specify / /speckit.plan / /speckit.tasks / /speckit.implement / Plan mode 比較
必要な準備
第5回完了（進級制作リポジトリに docs/prd/<feature-slug>.md / docs/adr/0001-<slug>.md / docs/plans/0001-<feature-slug>.md が push 済み）／Codespaces 上で Gemini CLI または GitHub Copilot CLI のどちらかが起動できる状態（2026-04-20 以降 Copilot Pro/Pro+/Student の新規申請が一時停止中のため、未認証の人は Gemini CLI 単体で進める）

この回のゴール

  • SDD（Spec-Driven Development）の核となる考え方——「仕様が実行可能な成果物になる」（公式: "specifications become executable, directly generating working implementations rather than just guiding them"）——を、自分の言葉で1〜2行で説明できる
  • GitHub 公式の Spec Kit（specify CLI）を進級制作リポジトリにセットアップできる
  • SDD ライフサイクル（定義 → 計画 → 分解 → 実行 → デバッグ）の各フェーズが、Spec Kit の公式スラッシュコマンドにどう対応するかを表で結びつけられる
  • 第5回で書いた PRD/ADR を素材に、/speckit.specify → /speckit.plan → /speckit.tasks までを Gemini CLI または Copilot CLI で実行し、仕様 → 計画 → タスク一覧が一筆書きで生成される様子を体感する
  • 第5回の Plan Mode（CLI 単体の読み取り専用設計モード）と、Spec Kit の SDD ライフサイクルを比較し、「実行前に計画を立てる」サイクルがどちらでどう違うかを口頭で言える
  • 進級制作に SDD で新機能を1つ追加する小演習を、/speckit.implement の途中まで進める（仕上げは家＋第7回 TDD 回で継続）

授業の流れ

2コマ連続（90分 + 90分 = 計180分）。途中休憩あり。

1限 前半 約40分

第5回の振り返り → SDD の核「仕様が実行可能な成果物になる」を理解する

第5回課題の共有（10分）

  • 第5回で push した docs/prd/ docs/adr/ docs/plans/ の3点セットを、近くの人と互いに見せる
  • 「PRD の成功基準が Plan Mode の出力にどこまで反映されたか」を1人1分で報告

Plan Mode だけでは届かないこと（10分）

  • 第5回の Plan Mode 出力は計画 markdownだった。これを実装に移すには、人間が:
    • 計画 markdown を読む
    • 1ステップずつ Gemini CLI または Copilot CLI に「これを実装して」と依頼する
    • 各ステップの差分をレビューしてコミットする
    を毎回手で繰り返す必要がある
  • 「計画は立てた、でもそこから先が手作業」がボトルネック。仕様・計画・タスク・実装が同じプロジェクト構造の中で連動して動く仕組みが欲しい

SDD の公式定義（10分）

  • GitHub Spec Kit 公式 README の冒頭（一次出典: github/spec-kit）から、SDD の定義を逐語で読む:
    "Spec-Driven Development flips the script on traditional software development... specifications become executable, directly generating working implementations rather than just guiding them."
  • 翻訳の要点:
    • flips the script: 従来の「コードが主役・仕様は補助資料」を逆転させる
    • specifications become executable: 仕様自体が実行可能になる
    • directly generating working implementations: 仕様から直接、動く実装を生成する
  • Spec Kit 公式 docs（github.github.com/spec-kit）のコアプロセス: "Spec → Plan → Tasks → Implement"。第5回までで体験した PRD/ADR/Plan Mode が、この一筆書きに繋がる素材だったと位置づけられる

今日のゴール提示（10分）

  • 今日は Spec Kit を進級制作リポジトリにセットアップして、第5回 PRD/ADR を素材に Spec → Plan → Tasks まで一筆書きで生成する。/speckit.implement はサイズの小さいタスクから1〜2件試す
  • SDD ライフサイクル（親ページの言い方: 定義 → 計画 → 分解 → 実行 → デバッグ）と Spec Kit の公式スラッシュコマンドの対応: 
    定義    →  /speckit.specify    (要件・ユーザーストーリーを書く)
計画    →  /speckit.plan       (技術的実装計画を作る)
分解    →  /speckit.tasks      (実行可能なタスク一覧に分解)
実行    →  /speckit.implement  (タスクを順番に実装)
デバッグ →  /speckit.analyze    (仕様と実装の整合性検証)
+ 前提  →  /speckit.constitution (プロジェクト方針・原則)
  • 仕上げに、Spec Kit の SDD ライフサイクル vs 第5回 Plan Mode の対比を口頭でまとめる（2限後半）
今日の合言葉: 「計画 markdown を読ませる」から「仕様から実装まで一筆書きにする」へ。手で繋いでいた4階層（指示／意図／判断／計画）が、今日からはツールで連動する。
1限 後半 約50分

Spec Kit セットアップ → /speckit.constitution と /speckit.specify

Spec Kit を進級制作リポジトリに導入（15分）

  • 公式の推奨インストール手順（一次出典: github/spec-kit README）。Codespaces ターミナルで次を実行: 
    # uv がまだ入っていなければ
curl -LsSf https://astral.sh/uv/install.sh | sh

# Spec Kit を一回限りで実行する（uvx は uv 同梱のツール実行コマンド）
# 安定運用したい場合は @vX.Y.Z でタグピン留めを推奨（公式 installation.md）
uvx --from git+https://github.com/github/spec-kit.git specify init --here --integration gemini
  • --here: カレントディレクトリ（=自分の進級制作リポジトリのルート）に初期化。新規プロジェクトの場合は specify init <PROJECT_NAME> でディレクトリを作る
  • --integration gemini: 今日のメインは Gemini CLI を選択（公式の現行オプション。古い解説に出てくる --ai は deprecated で警告が出る）。Copilot CLI を使う人は --integration copilot。Spec Kit は 30+ の AI coding agent に対応（公式 README: "Spec Kit works with 30+ AI coding agents" / 公式 docs: "30 integrations — Copilot, Gemini, Codex, Windsurf, Claude, Forge, Kiro, and more"）
  • 初期化後、リポジトリに .specify/（テンプレ・プロジェクト設定）と、対応 CLI に応じた スラッシュコマンド定義が追加される（Gemini CLI なら .gemini/commands/、Copilot CLI なら .github/agents/（.agent.md 形式のスラッシュコマンド本体）＋ .github/prompts/（companion）＋ .github/copilot-instructions.md 等）
  • git diff で生成物を一通り眺める。「Spec Kit は何を作ったのか」を3つ言える状態を作る

/speckit.constitution でプロジェクト原則を書く（10分）

  • Gemini CLI（または Copilot CLI）を起動し、最初に /speckit.constitution を呼ぶ。これはSDD の前提となるプロジェクトの方針・ガイドラインを整える
  • 第4回の GEMINI.md（指示）と似ているが、Spec Kit の constitution は「このプロジェクトでは何を絶対に守るか」に絞る。例:
    • 使用言語と理由（例: TypeScript＋React。既存進級制作と揃える）
    • テスト方針（例: 主要な振る舞いに最低1つテストを書く）
    • UI 原則（例: モバイル幅で崩れない）
    • 禁止事項（例: 外部API キーをコミットしない）
  • 3〜6行で十分。長くしない

/speckit.specify で仕様を書く（25分）

  • 第5回で書いた進級制作の小機能 PRD（docs/prd/<feature-slug>.md）を題材にする。Spec Kit に同じ機能を「仕様」として渡し直す
  • Gemini CLI / Copilot CLI で次のように呼ぶ: 
    /speckit.specify @docs/prd/<feature-slug>.md を仕様の元ネタにして、
このプロジェクトの仕様（ユーザーストーリーと受け入れ基準）を書いてください。
  • 第5回までに学んだ Memory Import の @ 構文を使って PRD を直接渡せる（公式: "Use the @ symbol followed by the path to the file you want to import"）。これで Spec Kit は PRD の「背景・成功基準・非ゴール」を踏まえた仕様を書く
  • 生成された specs/<NNN>-<feature-slug>/spec.md を開いて、PRD の成功基準がユーザーストーリー＋受け入れ基準として再構成されているか確認
  • 不足があれば /speckit.clarify を呼ぶ。Spec Kit があいまいな点を質問してきて、答えると仕様に追記される（公式 README に /speckit.clarify 記載あり）
PRD と spec.md の役割分担: PRD は「なぜ作るか」（意図）、Spec Kit の spec.md は「動くものとしての受け入れ基準」。同じ機能でも目的が違うので両方残す。PRD は将来 ADR と一緒に「なぜそう判断したか」を伝え、spec.md は「これが動けば完成」を伝える。
休憩 10分
2限 前半 約50分

/speckit.plan → /speckit.tasks で「仕様 → 計画 → タスク一覧」を一筆書きにする

/speckit.plan で技術的実装計画を生成（20分）

  • 同じ Gemini CLI / Copilot CLI セッションで /speckit.plan を呼ぶ。Spec Kit は spec.md を読んで、技術スタック・コンポーネント分割・データフロー・採用ライブラリを含む計画を生成する
  • 第5回の ADR を素材として渡せる: 
    /speckit.plan @docs/adr/0001-<slug>.md の決定事項に沿って計画してください。
  • 生成された plan.md を開く。第5回の Plan Mode 出力との違いを観察:
    • 第5回 Plan Mode: 1機能の実装ステップ列挙（人間が markdown を別保存）
    • Spec Kit /speckit.plan: 仕様ファイル（spec.md）と紐づいた計画として、プロジェクト構造に組み込まれた状態で出力される
  • 気になる点があれば、もう一度 /speckit.plan を呼んで「ここは案 B にしてほしい」と追加指示できる

/speckit.tasks で計画をタスク一覧に分解（15分）

  • /speckit.tasks を呼ぶと、plan.md を読んで実行可能なタスク一覧（tasks.md）が生成される
  • 各タスクは「ファイル名」「変更内容」「依存関係」「完了の判定条件」が書かれた粒度になっている
  • 生成された tasks.md を3つの観点で読む:
    • 仕様の受け入れ基準と1対1で紐づくタスクがあるか（漏れチェック）
    • 1タスクの粒度が「30〜60分で終わりそう」になっているか（大きすぎないか）
    • 依存関係が現実的か（先にやるべきものが後ろに置かれていないか）
  • 違和感があれば再生成、または tasks.md を手で編集する

/speckit.analyze で仕様と実装計画の整合性を検証（15分）

  • /speckit.analyze は SDD ライフサイクルの「デバッグ」フェーズに相当する公式コマンド（実装が始まる前でも、仕様・計画・タスクの整合性を機械的に検査できる）
  • 仕様で書いたユーザーストーリーが計画とタスクの両方でカバーされているか、矛盾している記述がないかを Spec Kit が指摘する
  • 第5回の Plan Mode では「人間がレビューする」段階だった整合性チェックを、/speckit.analyze は機械的に走らせて指摘する（最終的にどの3ファイルを直すかの判断・修正は人間の責任）
  • 指摘が出たら、spec.md / plan.md / tasks.md のどれを直すべきかを判断して修正する
3ファイル（spec / plan / tasks）の役割を覚える: 仕様（spec）は「動けば完成と判定できる条件」、計画（plan）は「どんな構造で作るか」、タスク（tasks）は「どの順番で何を実装するか」。整合性チェック（analyze）は3者がズレていないかの検査。この3階層は SDD の中核。
2限 後半 約30分

/speckit.implement で最初の1〜2タスクを実装＋Plan mode との対比

/speckit.implement で先頭1〜2タスクを実装させる（20分）

  • /speckit.implement は tasks.md を読んで順番に実装するコマンド。今日は最後まで走らせず、先頭1〜2タスクだけ進める
  • Gemini CLI / Copilot CLI どちらの場合も、実装中はファイル変更の差分が出るたびに人間がレビューして進める。AI まかせで一気通貫させない
  • レビュー観点:
    • spec.md の受け入れ基準を満たす変更になっているか
    • 第4回 GEMINI.md の指示（命名規則・スタイル）から外れていないか
    • 関係ないファイルが変更されていないか
  • 1タスク完了したら git add -p で差分を眺めてからコミット。「Spec Kit が作った差分」と「自分が選んで採用した差分」を意識して分ける
  • 残りのタスクは家＋第7回（TDD 基礎）以降で継続する

Plan mode と SDD ライフサイクルの対比（10分）

  • 第5回までのPlan Mode（公式: "a read-only environment for architecting robust solutions before implementation"）と、今日のSpec Kit による SDD ライフサイクルの違いを表で整理:
    観点 Plan mode（第5回） SDD ライフサイクル（Spec Kit）
    起動方法 Gemini CLI: /plan または Shift+Tab
    Copilot CLI: Shift+Tab    		 specify init で導入後、/speckit.* スラッシュコマンド群
    出力 1本の計画 markdown 仕様（spec.md）／計画（plan.md）／タスク（tasks.md）の3ファイル
    整合性検証 人間がレビュー /speckit.analyze が自動検査
    適する場面 1機能の実装計画を素早く作る 機能サイズが大きい・複数タスクに分解する必要がある
  • 結論: 両方使う。小さい機能や試作は Plan mode、ある程度サイズがあって品質を担保したい機能は Spec Kit。「実行前に計画を立てる」というサイクル自体は両方に共通する
実装は来週以降: 今日は 先頭1〜2タスクまで。残りは家＋第7回（TDD 基礎）でテストを書きながら進める。Spec Kit が一気に最後まで実装してしまえる魅力に流されないこと。「責任あるコード」は差分を毎回レビューする姿勢から始まる。
まとめ 約10分

振り返り＆次回予告

  • 今日のキーワード: SDD / Spec Kit / /speckit.specify / /speckit.plan / /speckit.tasks / /speckit.implement / /speckit.analyze / Plan mode との対比
  • 覚えてほしいこと: 「仕様が実行可能な成果物になる」。仕様（spec）→ 計画（plan）→ タスク（tasks）→ 実装（implement）が、ばらばらの markdown ではなく連動する一筆書きになる
  • 2026年5月時点の Spec Kit はオープンソースの初期段階で活発に開発中（GitHub Stars 100k 近い規模、30 以上の AI coding agent に対応）。仕様・コマンド名は変わる可能性があるため、迷ったら公式 README と公式 docsを確認する
  • 次回（第7回）: テスト駆動開発（TDD）基礎。今日 tasks.md に並んだタスクを、Red → Green → Refactor サイクルで実装していく。テスト観点（正常系・異常系・境界値）の設計を学ぶ
  • 家での発展（任意）: 残ったタスクを /speckit.implement で1〜2件追加で進める。差分が大きくなったら、自分の手で1コミットに収まるサイズに分割する練習にもなる

課題・次回までにやること

必須
Spec Kit セットアップ済みリポジトリを push

進級制作リポジトリに .specify/ と対応 CLI のスラッシュコマンド定義（.gemini/commands/ または .github/agents/ 等）が含まれる状態で push。uvx による初期化の実行ログ（成功表示）を任意の docs/speckit-init.txt として残してもよい。

必須
仕様・計画・タスクの3ファイルを push

specs/<NNN>-<feature-slug>/spec.md / plan.md / tasks.md の3ファイルを push。第5回 PRD の成功基準と spec.md の受け入れ基準が対応しているか目視確認。

必須
/speckit.analyze の検査結果を要約してメモ

/speckit.analyze の出力を docs/speckit-analyze.md として保存（または README にメモ）。指摘があれば、どの3ファイル（spec/plan/tasks）をどう直したかも1〜2行で記録する。

推奨
2〜3タスクまで /speckit.implement を進める

家で先頭タスクの続きを実装。差分が大きい場合は1コミット30分〜1時間で収まるサイズに分けてコミット。第7回 TDD 回では、各タスクに対するテストを後追いで書いていく。

推奨
specify check でツール環境を点検

Spec Kit には環境点検コマンド specify check がある。Codespaces 上で実行し、自分の環境で Gemini CLI または Copilot CLI が Spec Kit から認識されているかを確認。出力を docs/speckit-check.txt として残してもよい。
