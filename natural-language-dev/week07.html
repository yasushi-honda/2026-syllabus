テスト駆動開発（TDD）基礎

Week 7 木曜 1・2限
テーマ
第6回 Spec Kit で並べた tasks.md を、Red → Green → Refactor サイクルで実装する。テスト観点（正常系・異常系・境界値）を人間が設計し、AI にテストとプロダクションコードの両方を書かせて、観点の網羅性は人間が判断する役割分担を体感する
キーワード
TDD / Red → Green → Refactor / テスト観点（正常系・異常系・境界値）/ tasks.md と TDD の接続 / AI に書かせる + 人間が観点を検証 / Vitest など既存テストランナー
必要な準備
第6回完了（進級制作リポジトリに specs/<NNN>-<feature-slug>/spec.md plan.md tasks.md が push 済み）／進級制作で使うテストフレームワーク（Vitest / Jest / pytest 等）が npm test または pytest 等のコマンドで起動できる状態／Gemini CLI または GitHub Copilot CLI のどちらかが起動できる状態

この回のゴール

  • TDD の基本サイクル Red → Green → Refactor を、自分の言葉で1〜2行で説明できる（Red = 失敗するテストを先に書く／Green = テストを通す最小実装／Refactor = テストを保ったまま整える）
  • テスト観点の3分類——正常系・異常系・境界値——を、自分の進級制作の1機能に当てはめて列挙できる
  • 第6回 tasks.md の先頭1〜2タスクを Red → Green → Refactor の1サイクル分実装し、テスト・実装・tasks.md の [x] マーキングまで push できる
  • AI（Gemini CLI / Copilot CLI）にテストを書かせる際、「コードを書く仕事」と「観点の網羅性を判断する仕事」の境目を意識できる
  • 今日書いたテストが、第8回（ハーネスエンジニアリング入門）で GitHub Actions のセンサーとして毎回走る仕組みに繋がることを理解する

1限 前半 約40分

第6回の振り返り → TDD の核「テストを先に書く」を公式定義で押さえる

第6回課題（Spec Kit）の共有（10分）

  • 第6回で push した spec.md / plan.md / tasks.md の3点を、近くの人と互いに見せる
  • 家で /speckit.implement の続きを進めた人は、「先頭タスクが実装まで進んだか」「関係ないファイルが変更されなかったか」を1人1分で報告
  • よくある体感を共有: 「実装まで一気に走らせたら関係ない場所まで触られた」「テストが付いてこない実装になった」「Refactor で振る舞いが変わってしまった」

TDD の公式定義を読む（15分）

  • 一次出典: Martin Fowler — "TestDrivenDevelopment" から逐語:
    "Test-Driven Development (TDD) is a technique for building software that guides software development by writing tests."
  • 翻訳の要点: テストを書くことが、ソフトウェア開発そのものを導く（guide する）。テストは「後付けの検証」ではなく「開発を進めるためのハンドル」
  • サイクルは Kent Beck の "Test-Driven Development: By Example"（2002）以来、3フェーズで定義される（一次出典: Wikipedia — Test-driven development の "TDD cycle" 節）: 
    Red       →  失敗するテストを書く（実装はまだない or 通らない）
Green     →  テストを通す最小実装を書く（賢くしようとしない）
Refactor  →  テストが通る状態を保ったまま、コードを整える
  • 第6回までで tasks.md には「何を実装すべきか」が並んだ。今日は各タスクを 「実装の前に Red を書く」から始める

今日のゴール提示（15分）

  • 今日は tasks.md の先頭1〜2タスクで Red → Green → Refactor を1サイクル回す。2タスク目以降は家＋第8回（ハーネス）以降で継続
  • テスト観点の3分類（1限後半で詳しく扱う）を覚える: 正常系 / 異常系 / 境界値
  • AI（Gemini CLI / Copilot CLI）にテストを書かせる際の役割分担:
    • AI が書く: テストコードの形式・assertion の使い方・mock の組み立て
    • 人間が判断する: 観点の網羅性（境界値が落ちていないか、異常系の入力パターンが現実的か）
  • Anthropic Engineering 公式 ("Claude Code: Best practices for agentic coding") でも、TDD は AI コーディングと相性のよい主要ワークフローとして紹介されている。テストを先に書いて固定し、AI が実装を反復する流れは Gemini CLI / Copilot CLI でも同じく機能する
今日の合言葉: 「テストの色（Red / Green）を意図的に作る」。Red を意図して作って、Green を確認して初めて、Refactor が安全な作業になる。色を見ずに書いたテストは、後でリファクタを守ってくれない。
1限 後半 約50分

テスト観点（正常系・異常系・境界値）と最初の Red テスト

テスト観点の3分類を覚える（15分）

  • ① 正常系（Happy Path）: 想定通りの入力で、想定通りの出力が返るケース。「動くことの確認」ではなく「仕様を満たすことの確認」
  • ② 異常系（Error Path）: 想定外の入力（null / undefined / 空文字列 / 空配列 / 型不一致 / 認証なし 等）が来たときの振る舞いを宣言するケース
  • ③ 境界値（Boundary）: 仕様の境目（最小・最大・±1 ・0・1要素・上限値）でも壊れないこと
  • 例: 仕様「ユーザー名は3〜20文字」のとき、境界値テストは 2文字（NG）・3文字（OK）・20文字（OK）・21文字（NG）の4点。1点だけでは境界の「両側」を守れない
  • 本授業のグローバル方針（~/.claude/CLAUDE.md Test First 節）でも: 「境界値（最小/最大/±1）と異常系（null/undefined/空）を必ず含める」が MUST として書かれている
  • 仕様の受け入れ基準（spec.md）を見直して、3分類のどれにあたるかを脇にメモすると、テスト名を考えるときに迷わない

tasks.md の先頭タスクで Red テストを書く（30分）

  • 進級制作の tasks.md の先頭タスク1件を選ぶ。複数タスクをまたぐと色（Red/Green）が混ざって追えなくなるため、必ず1件ずつ
  • 既存のテストフレームワークで *.test.ts（または test_*.py 等）を新規作成。ファイル名は実装ファイル名と対応させる（foo.ts → foo.test.ts）
  • Vitest を使う場合の基本形（一次出典: Vitest 公式）: 
    import { describe, it, expect } from 'vitest';
import { formatUserName } from './formatUserName';

describe('formatUserName', () => {
  it('正常系: 想定通りの入力で正しく整形される', () => {
    expect(formatUserName('  yamada  ')).toBe('yamada');
  });
  it('異常系: null が来たら空文字列を返す', () => {
    expect(formatUserName(null as unknown as string)).toBe('');
  });
  it('境界値: 上限21文字は切り捨てる', () => {
    expect(formatUserName('a'.repeat(21))).toHaveLength(20);
  });
});
  • AI に依頼する場合のプロンプト例（@ Memory Import で spec.md / tasks.md を渡す）: 
    @specs/0001-<feature-slug>/spec.md と @tasks.md の先頭タスクを読んで、
Vitest でテストを書いてください。次の3分類を最低1件ずつ:
- 正常系: 仕様通りの入力で期待通りの出力が返る
- 異常系: null / 空 / 型不一致が来たときの振る舞い
- 境界値: 仕様の境目（最小・最大・±1）でも壊れない

実装ファイルはまだ書かないでください。テストだけを生成してください。
  • 生成されたテストを npm test（または pytest）で実行 → すべて失敗することを確認。これが Red
  • 「全部が失敗していない」場合は要注意:
    • テスト名が仕様を表していない（実装と無関係に通る）
    • すでに実装が部分的に存在している
    • AI が空のテストを書いて Pass にしてしまっている（expect(true).toBe(true) 等）

AI に書かせる仕事と人間がやる仕事の境目（5分）

  • AI が書く: テストコードの形（describe / it / expect の組み立て・mock）
  • 人間が判断する: 観点の網羅性（境界値が落ちていないか・異常系の入力パターンが現実的か）
  • 第6回 spec.md の受け入れ基準1つ1つを指で追って、対応するテストがあるかを確認する
Red を意図して作る: 失敗するテストを書くのは「下手だから」ではなく「これからこの仕様を作る」という宣言。Red の状態を一度通過させずに実装に進むと、テストが実装に都合よく書き換えられてしまう。
休憩 10分
2限 前半 約50分

Green → Refactor の1サイクルを完走させる

Green: 最小実装でテストを通す（25分）

  • Gemini CLI / Copilot CLI に依頼: 
    @<テストファイルパス> を通すための最小実装を書いてください。
賢く書こうとせず、テストが通るだけのコードで構いません。
関係ないファイルは変更しないでください。
  • npm test で全テストが通ることを確認（Red → Green）。色が変わる体感を意識する
  • 「テストを通すだけ」が原則。仕様外の装飾（過剰な抽象化・将来のための拡張ポイント）は、この段階では避ける——後の Refactor で整えるのが TDD の順番
  • テストが通らない場合の選択肢:
    • 実装側を直す（原則こちら）
    • テスト側の誤りを直す（assertion の数値ミス等）。ただし「テストが通らないからテストを変える」のは AI に任せず人間が判断——テストを実装に都合よく書き換えると、TDD のサイクル自体が壊れる
  • 第4回 GEMINI.md の指示（命名規則・スタイル）から実装が外れていないかも併せて確認

Refactor: テストを保ったままコードを整える（15分）

  • AI に依頼: 
    現在のテストを保ったまま、実装の可読性と命名を改善してください。
変更後は npm test がすべて通ることを確認してから差分を出してください。
振る舞いを変える変更は提案しないでください。
  • 各 Refactor の差分ごとに npm test を走らせ、緑のままであることを確認する。これが Red で書いたテストの最大の役目——「Refactor で振る舞いが変わってしまった」を検出するセンサーとして働く
  • Refactor の方向性:
    • マジックナンバーを定数に
    • 重複コードの整理（同じ判定ロジックが2箇所以上に出ていたら関数化）
    • 関数の責務を1つに（1関数1責務）
    • 命名の改善（変数名・関数名）
  • 注意: Refactor は「整える」までで止める。ここで仕様を超えた機能追加に行ってしまうと、テストが守る範囲を超えてしまい、安全網が外れる

2サイクル目に入る（10分）

  • tasks.md の2番目のタスクを取り出し、再び Red から始める
  • 1サイクル目で「これは AI が書いた」「これは自分が判断した」の境目を意識しながら進める
  • 時間切れの場合は2サイクル目の Red だけで終わって OK（家で続ける）
  • 2サイクル目を終えたタスクは tasks.md 上で [ ] → [x] に更新してコミット（グローバル CLAUDE.md MUST: 「Spec完了の定義 → tasks.md の全チェックボックスを [x] に更新してからコミット」に準拠する練習）
3フェーズはコミットを分ける: 1サイクルを test: (Red) → feat: (Green) → refactor: (Refactor) の3コミットに分けると、後でログを読んだ自分（や将来のレビュアー）が「テストが先に来ていた」「Refactor で振る舞いが変わっていない」を確認できる。
2限 後半 約30分

AI 生成テストの観点検証 → 第8回（ハーネス）への接続

AI に観点拡張を依頼して、人間が網羅性を判定（20分）

  • 1サイクル目のテストファイルを開いて、AI に追加観点を提案させる: 
    現在のテストにどんな観点が抜けていますか？
正常系・異常系・境界値の3分類で抜けがあれば、テストを追加してください。
なぜそのテストが必要かも1行で説明してください。
  • AI の提案を人間がレビューして取捨選択する:
    • 採用: 仕様（spec.md）の受け入れ基準に対して現実的な観点
    • 却下: 「AI が書きたいから書いた」レベルの過剰テスト。「このテストがなぜ必要か」を1行で説明できないテストは、ノイズになるので消す
  • 残ったテストが Red になることを確認 → Green → Refactor で1サイクル回す（時間があれば）
  • ここで「AI にテストを書かせる」と「人間がテスト観点を検証する」の役割分担を改めて体感する。観点の網羅性は人間が判断する責任領域
  • 授業概要にあった「責任あるコード」の最初の具体例: 異常系・境界値を最低1つは書いた＝「想定外でも壊れない／仕様の境目を意識した」という設計上の宣言

第8回（ハーネスエンジニアリング）への接続（10分）

  • 今日書いたテストは、第8回で GitHub Actions のセンサーとして毎回 PR ごとに自動実行される仕組みを作る
  • 親ページ用語のおさらい:
    • ガイド（事前制御）: GEMINI.md / .geminiignore / サンドボックス / ブランチ保護 = AI が触る前に「これはやるな・これを守れ」を伝える
    • センサー（事後検証）: GitHub Actions の test / lint / build = AI が触った後で「振る舞いが壊れていないか」を検出する
  • 第8回では Gemini CLI の Hooks（BeforeTool / AfterTool）でツール呼出の前後に検証を差し込む仕組みも実装する
  • 結論: 「テストを書く」は出発点で、「テストが必ず走る環境を作る」が次の段階
テストの最大の役目は色の管理: Red は「これからこの仕様を作る」の宣言、Green は「仕様を満たした」の証拠、Refactor 中の Green 維持は「振る舞いを変えていない」の証拠。テストが守る範囲だけが、安全にリファクタできる範囲。
まとめ 約10分

振り返り＆次回予告

  • 今日のキーワード: TDD / Red → Green → Refactor / テスト観点（正常系・異常系・境界値）/ tasks.md と TDD の接続 / AI に書かせる + 人間が観点を検証
  • 覚えてほしいこと: テストは「書いたら終わり」ではなく「色（Red / Green）を見るための道具」。Red を意図して作って、Green を確認することで、後の Refactor が安全な作業になる
  • 「責任あるコード」の最初の具体例:
    • 異常系を最低1つ書いた = 「想定外でも壊れないことの宣言」
    • 境界値を最低1つ書いた = 「仕様の境目を意識した実装の宣言」
  • 次回（第8回）: ハーネスエンジニアリング入門。今日書いたテストを GitHub Actions で毎回 PR ごとに走らせる仕組み・Gemini CLI Hooks（BeforeTool / AfterTool）で機密情報コミット阻止・ツール引数検証・監査ログを実装する
  • 家での発展（任意）: 残ったタスクを tasks.md の順に Red → Green → Refactor で1〜2件進める。サイクルごとに3コミットに分ける練習にもなる

課題・次回までにやること

必須
1サイクル分の Red → Green → Refactor を push

進級制作リポジトリに、tasks.md 先頭タスクに対する Red テスト（最低: 正常系1件・異常系1件・境界値1件）、Green を満たす最小実装、Refactor 済みコードの3点を push。コミットは test: → feat: → refactor: の3コミットに分けるのが推奨だが、1コミットにまとめても OK。

必須
tasks.md の進捗を [x] に更新

完了したタスクのチェックボックスを [ ] から [x] に更新してコミット（グローバル CLAUDE.md MUST 準拠の練習）。残りのタスクは [ ] のままで OK。

必須
テストの観点メモを README に追記

README.md または docs/testing.md に、今日書いたテストの3観点（正常系・異常系・境界値）を1〜2行ずつ、対応するテスト関数名と一緒に列挙する。AI に観点拡張を依頼した結果も 採用 / 却下の判断を含めて記録する。

推奨
2サイクル目以降を家で進める

tasks.md の2〜3番目のタスクを家で Red → Green → Refactor で進める。差分が大きい場合は、1コミット30分〜1時間で収まるサイズに分けてコミット。

推奨
「振る舞いを変えない Refactor」を意識的に1回試す

テストが緑の状態で、AI に「振る舞いを変えずに命名・構造だけ整えて」と依頼。差分ごとに npm test を走らせて、緑のまま整える体験を積む。途中で赤になったら、何が振る舞いを変えたかを観察するのが学び。
