Vibe Codingの限界とGEMINI.mdで落ち着かせる

Week 4 木曜 1・2限
テーマ
Gemini CLI の出力のブレを体感し、GEMINI.md という置き手紙で落ち着かせる
キーワード
Vibe Coding / 出力のブレ / GEMINI.md / instructional context / Before / After 比較
必要な準備
進級制作リポジトリがCodespacesで開ける状態・Gemini CLIの認証が完了している状態（第1回完了）・第3回の docs/cli-comparison.md を保存済み

この回のゴール

  • Vibe Coding で実際にやらかしてもらい、Gemini CLI の出力のブレ（使用言語の混在・スタイル逸脱・関係ないファイルの変更）を自分の目で確認する
  • GEMINI.md が「Gemini CLI が起動時に自動で読む置き手紙」であることを理解する
  • 3〜5 行の最小 GEMINI.md を自分の進級制作に書ける
  • 同じ依頼を Before/After で再実行し、出力が落ち着く瞬間を体感する
  • 「指示を毎回書かなくても、ある程度言うことを聞いてくれる状態」を自分の手で作れるようになる

授業の流れ

2コマ連続（90分 + 90分 = 計180分）。途中休憩あり。

1限 前半 約40分

前回の振り返り＆「Gemini CLI、雑だなと思った瞬間」共有

前回課題の共有（10分）

  • 第3回の docs/cli-comparison.md（使い分け方針メモ）から、印象に残った発見を1つ口頭共有
  • Copilot CLI が動かなかった人は Gemini CLI 単体の所感でOK

「Gemini CLI、雑だなと思った瞬間」を出し合う（15分）

  • 第3回 Vibe Coding で気になった出力を、近くの人とペアで2〜3個ずつ共有
    • 頼んでないファイルまで触られた
    • 使ってる言語と違う言語で書かれた
    • インデント・命名がプロジェクトとズレた
    • 関係ないライブラリを勝手に追加された 等
  • 「これって自分が悪いの？AI が悪いの？」を一緒に考える——答えは 「指示文だけだと AI が前提を知らないから」

今日のゴール提示（15分）

  • 今日のキーワードは GEMINI.md。これは Gemini CLI が起動するときに自動で読む置き手紙。公式は「a powerful feature for providing instructional context to the Gemini model」（Gemini モデルに指示用のコンテキストを与えるための機能）と説明している
  • 動作の核心は「見つけた全ファイルを連結し、毎プロンプトでモデルに送信する」こと（公式: concatenates the contents of all found files, and sends them to the model with every prompt）。一度書けば、各依頼の前段に毎回くっついて AI に渡る
  • 毎回チャット欄で「TypeScript で書いて」「インデントは2スペースで」と言わなくても、書いておけば毎回参照してくれる
  • 今日は 裸で1回 → GEMINI.md を書く → 同じ依頼を再投入して比べる という Before/After 形式で進める
今日の合言葉: 「AI への置き手紙」。難しいファイルではなく、書いておくと AI が毎回読んでくれるメモです。
1限 後半 約50分

裸の Vibe Coding：何も書かずに小機能を追加してみる

準備（5分）

  • 進級制作リポジトリで git status がクリーンな状態を確認。途中の変更があれば git stash しておく
  • これから1限後半と2限後半で同じ依頼を2回投げるので、依頼内容は1つ決めて固定する

お題を決める（5分）

  • 進級制作に「2〜10 行で済みそうな小さな改善」を 1 つ選ぶ。例:
    • ヘッダーに「お問い合わせ」リンクを追加
    • フォームに「名前」欄のバリデーションを追加
    • READMEに「使い方」セクションを追記
    • 関数を 1 つリネームして呼び出し元を全部直す
    • エラーメッセージを利用者向けの言葉に書き直す
  • 依頼文は短めの自然言語で OK（例: 「ヘッダーにお問い合わせリンクを追加してください」）

Vibe Coding 実行：GEMINI.md を書かないまま依頼（25分）

  • Gemini CLI を起動（npx @google/gemini-cli）して、決めた依頼文を投げる
  • AI が書いたコードをそのまま受け入れる気持ちで進める。完璧を目指さない
  • 動作確認は気が向いたらでOK——今日は出力のブレを観察するのが主目的

ブレを記録する（15分）

  • 進級制作リポジトリに docs/vibe-before-after.md を作り、以下のテンプレで Before セクションを書く: 
    # Vibe Coding Before/After

## 依頼文
（実際に投げた依頼を貼る）

## Before（GEMINI.md なしで投げた結果）
- 気になった点①: 言語が混ざった（◯◯と書きたいのに △△ になった）
- 気になった点②: スタイルが違う（インデント／クォート／命名）
- 気になった点③: 関係ないファイルを触られた／余計なライブラリが入った
- その他の発見:
  • 気になった点が 3 つ以上 書ければOK。ここで書いた不満が、2 限で書く GEMINI.md の素材になる
  • 変更を採用する／しないは自由。git stash で一旦置いておくと比較しやすい
うまくブレない人へ: AI が綺麗に書いてくれてしまった人は 当たり回。日替わりで挙動が変わるので、別のお題で試すか、近くの人の「やらかし」を見学すれば OK です。
休憩 10分
2限 前半 約50分

GEMINI.md を書いてみる——3〜5 行から

公式の最低限（10分）

  • GEMINI.md は Gemini CLI が起動時に自動で読む context file。中身は instructional context（指示用コンテキスト）と呼ばれ、複数ファイルが階層構造で読み込まれ、連結（concatenate）されて毎プロンプトでモデルに送られる。この合成された指示文の塊を公式は hierarchical memory と呼ぶ
  • 用語整理: GEMINI.md がファイル本体（context file）／その中身が指示用コンテキスト（instructional context）／全 GEMINI.md を連結したものが階層的メモリ（hierarchical memory）
  • 3 段階の階層が公式に定義されている:
    1. グローバル: ~/.gemini/GEMINI.md（自分のホーム）。全プロジェクト共通の「自分の好み」を書く場所
    2. ワークスペース: 開いているプロジェクトのルート（およびその親ディレクトリ）に置いた GEMINI.md。今日書くのはここ
    3. Just-in-time: AI がツールでアクセスしたファイルの祖先ディレクトリにあるもの（自動で拾われる）
  • ファイル名は GEMINI.md がデフォルト。settings.json の context.fileName で AGENTS.md 等に変更可能（配列で ["AGENTS.md", "CONTEXT.md", "GEMINI.md"] のように複数指定もできる）だが、今日は標準のままで OK
  • Gemini CLI 起動中は /memory show でいま AI に渡される指示文の全文（連結された階層的メモリ）を確認できる。読み込まれた GEMINI.md の個数は CLI のフッターにも表示される

講師の最小サンプルを見る（10分）

  • 板書例（あえて短くする）: 
    # このプロジェクトの前提

## 言語
- TypeScript で統一しています。JavaScript で書かないでください。

## スタイル
- インデントは半角スペース2つ
- 文字列はシングルクォート
- 関数名は camelCase

## 守ってほしいこと
- 依頼されていないファイルは変更しない
- 既存のテストを壊さない
  • 長く書けば良いものではない。長くするほど毎プロンプトで送信される指示が膨らみ、第2回で扱った U字型精度カーブの影響で AI が真ん中の指示を読み飛ばしやすくなる。まず3〜5 行・最大 1 画面で OK（教材としての経験則）
  • 公式ドキュメントにも例として「When you generate new TypeScript code, follow the existing coding style」「Ensure all new functions and classes have JSDoc comments」など、短い指示を箇条書きで積み重ねる書き方が例として示されている（公式は「推奨」とは書いていない、あくまで例）

各自が書く（30分）

  • 1 限後半でメモした「気になった点 ①②③」を GEMINI.md の文章に変換する
    • 「言語が混ざった」→ このプロジェクトは Python のみで書いています。他言語のコードを混ぜないでください。
    • 「インデントが違う」→ インデントは半角スペース 4 つです。
    • 「関係ないファイルを触られた」→ 依頼されていないファイルは変更しないでください。
  • 進級制作のルートに GEMINI.md を保存。3〜5 行で十分（書き過ぎない）
  • 書き終わったら git add GEMINI.md しておく（commit はあとで）
書き方に迷ったら: 「自分が新人にプロジェクトを引き継ぐとき、最初に伝えること 3 つ」を書くつもりで。コードレビューで毎回指摘されたくないことが、一番効くルールです。
2限 後半 約30分

同じ依頼を再投入して Before/After を比較する

Gemini CLI を再起動（5分）

  • 新しい GEMINI.md を読み込ませるため、起動中の Gemini CLI を一度終了して再起動（または起動したまま /memory reload を実行。refresh もエイリアスで同じ動作だが、公式の正式名は reload）
  • 再起動後、/memory show で書いた指示が AI に渡る指示文に含まれているかを確認する（公式仕様: 連結された hierarchical memory の全文表示）

同じ依頼をもう一度投げる（15分）

  • 1 限後半で固定した依頼文をそのまま投げ直す（コピペで OK）
  • 1 限後半の git stash をしている人は、ここで diff を取ると比較しやすい

After を記録する（10分）

  • docs/vibe-before-after.md に After セクションを追加: 
    ## After（GEMINI.md ありで投げた結果）
- ①は…… 改善した／変わらなかった
- ②は…… 改善した／変わらなかった
- ③は…… 改善した／変わらなかった
- 新しく気づいたこと:
- 効かなかった指示があれば、GEMINI.md にどう書き足したいか:
  • 「効かなかった指示」が見つかったら、GEMINI.md を 1〜2 行追記してもう一度同じ依頼を投げてもよい（時間が許す範囲で）
  • commit しておく: git add docs/vibe-before-after.md GEMINI.md && git commit -m "Vibe Coding の Before/After を記録"
まとめ 約10分

振り返り＆次回予告

  • 今日のキーワード: 裸の Vibe Coding / 出力のブレ / GEMINI.md / instructional context / Before / After
  • 覚えてほしいこと: GEMINI.md は AI への置き手紙。短く始めて、効かなかったら 1 行ずつ足す
  • 「指示を毎回書かなくて済む状態」が少しでも作れたら、今日の目的は達成
  • 次回（第5回）: PRD（製品要求仕様書）と ADR——今日は「AI にやってほしいこと」を書いた。次回は「人間に向けて、なぜそうしたかを書く」回
  • 気が向いたら、ホームの ~/.gemini/GEMINI.md に「全プロジェクト共通の自分の好み」を書いてみる（任意）

課題・次回までにやること

必須
GEMINI.md の初版を push

進級制作リポジトリのルートに GEMINI.md を作成して push。3〜5 行で構わない。最低限「使用している言語」「守ってほしい書き方のルール」「触ってほしくない範囲」のうち 1 項目以上が書かれていること。

必須
docs/vibe-before-after.md の提出

Before（GEMINI.md なしの結果） / After（GEMINI.md ありの結果）の比較メモを push。気になった点が 3 つ以上記録されていること。

推奨
ホームの ~/.gemini/GEMINI.md を書いてみる

全プロジェクト共通の「自分の好み」（例: 「日本語で説明してください」「変更を加える前に計画を見せてください」等）を 2〜3 行で。書きすぎないのがコツ。

推奨
効かなかった指示を 1 つ追記して再挑戦

After で「変わらなかった」と感じた点があれば、GEMINI.md に 1 行だけ追記して、家でもう一度同じ依頼を投げてみる。何が効いて何が効かないかの感覚は、回数を重ねないと身につかない。
