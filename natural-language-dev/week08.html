本回の重要な変更点：Gemini CLI → Antigravity CLI

2026-05-19（Google I/O 2026）に Google が発表: Gemini CLI の機能は Antigravity CLI（コマンド名 agy）に引き継がれ、個人・Pro・Ultra・無料ユーザー向けの Gemini CLI サービスは 2026-06-18 で停止します。Enterprise（Code Assist Standard / Enterprise / 有料 API key）のみ Gemini CLI を継続利用できます。第7回までは Gemini CLI で進めてきましたが、本回（第8回）から Antigravity CLI に切り替えます。GEMINI.md は引き続きそのまま動作するなど互換性は高く、移行コマンド agy plugin import gemini で旧設定の自動変換ができます（公式: Google Developers Blog / Antigravity CLI 移行ガイド）。

この回のゴール

  • ハーネス＝「AI エージェントを長時間安全に走らせるための足場（ガイド＋センサー）」だと、自分の言葉で1〜2行で説明できる
  • ガイド（事前制御）とセンサー（事後検証）の違いを、第7回までに自分が触ったファイル名を例に挙げて説明できる
  • 進級制作環境を Antigravity CLI（コマンド agy）に切り替え、agy plugin import gemini で第7回までの設定・拡張を自動変換できる
  • 進級制作リポジトリに .geminiignore を1ファイル追加して、AI が触ってはいけない場所を宣言できる
  • 第7回で書いたテストを GitHub Actions 上で push のたびに自動実行する .github/workflows/test.yml を1本作って push できる
  • Antigravity CLI には Hook（plugin 内の hooks.json で定義し、/hooks で active を確認できる仕組み）が存在することを知り、ハーネスの「閘門（こうもん）」として将来発展させる余地を持って帰る
  • 「AI が触る前に止める（ガイド）」と「AI が触った後で検出する（センサー）」の両輪が揃って初めて、AI に長時間作業を任せられる感覚を掴む

ガイド（事前制御）— .geminiignore とブランチ保護

.geminiignore を作る（25分）

  • 一次出典: gemini-cli/docs/cli/gemini-ignore.md（旧 Gemini CLI 公式）。GEMINI.md と同じく Antigravity CLI でも引き続き機能する（公式移行ガイドで GEMINI.md の継続使用が明記されていることから類推、Antigravity 側の対応状況の最終確認は次節）
  • 公式説明の要点（旧 Gemini CLI docs ベース）:
    • 構文は .gitignore と同じ glob パターン（行末コメント・否定 ! ・ディレクトリ末尾の / 全対応）
    • 記述したファイルは @（ファイル参照）コマンドや read_many_files などのツール経由でアクセスできなくなる。Git からは普通に見える（.gitignore とは別物）
    • 変更を反映するにはセッションの再起動が必要
  • 進級制作リポジトリのルートに .geminiignore を新規作成し、最低限以下を入れる: 
    # 依存物・ビルド成果物
node_modules/
dist/
build/
.cache/

# 機密情報
.env
.env.*
*.pem
*.key
secrets/

# ローカル設定・履歴
.vscode/
.idea/
*.log
  • 進級制作で追加で AI に触らせたくない場所（例: 個人の調査メモ・本人写真・古い実験コード）があれば、自分の判断で1〜2行追記
  • commit して push。コミットメッセージは chore: add .geminiignore 等で短く
  • 注意（Antigravity CLI 利用者）: 公式 Antigravity docs の現バージョンには .geminiignore の取り扱いの独立 reference が見当たらないため、想定通り効いているかを agy 起動後の @ コマンドで「.env を見せて」と依頼して無視されることを実機で確認する。万一読まれてしまう場合は Troubleshooting 参照

ブランチ保護を有効化（20分）

  • 一次出典: GitHub Docs ja — 保護されたブランチについて
  • 進級制作リポジトリの GitHub ページ → Settings → Branches → Add classic branch protection rule（または Rulesets）で main を対象に以下を最低限有効化:
    • Require a pull request before merging（PR 経由でないと merge できない）
    • Require status checks to pass before merging（後で作る GitHub Actions が緑になるまで merge できない／Actions が初回 push 後に「ステータスチェック候補」として選べるようになる）
  • これにより、AI が git push origin main を実行しても拒否される——「人間が PR をレビューする経路を物理的に必須化」する
  • リポジトリの可視性とプラン: Free private リポジトリでも本授業で使うPull Request 必須化とstatus checks 必須化は利用可能（2022 年以降の classic branch protection）。push できる人を制限する機能（Restrict who can push to matching branches）や Rulesets の一部高度機能は Free 組織では public 限定／Team・Enterprise 以上で全リポジトリ利用可、というプラン依存があるため、UI に表示されない項目があった場合は規範として「main に直 push しない」を GEMINI.md に明記することで補う

サンドボックスの話（5分・口頭）

  • Antigravity CLI には permissions & sandbox という公式機能があり、--sandbox フラグや toolPermission 設定（request-review / proceed-in-sandbox / always-proceed / strict の4プリセット）で AI のコマンド実行をどこまで自動許可するかを制御できる（一次出典: Antigravity CLI — Permissions & Sandbox）
  • 今日は触らないが、本番リポジトリで Vibe Coding するときは「壊れていい環境」で動かすのが鉄則という認識を持つ。Codespaces を使う＝最低限の隔離は確保、Antigravity の --sandbox や toolPermission: "strict" まで含めて検討するのは次の段階
.geminiignore は .gitignore とは別: .gitignore は「Git にコミットしない」、.geminiignore は「AI のツールから読まない」。役割が違うので、両方の管理が必要。.env は 両方に書く。

センサー（事後検証）— GitHub Actions で第7回のテストを毎回走らせる

GitHub Actions の公式定義（5分）

  • 一次出典: GitHub Docs ja — GitHub Actions のクイック スタート
  • 要点: リポジトリのイベント（push / PR / schedule 等）をトリガーに、ワークフロー（YAML で定義した一連の処理）が自動実行される仕組み
  • ファイル配置: .github/workflows/<任意の名前>.yml。複数ファイル可
  • 本授業のテーマでの位置づけ: 第7回で書いたテストは「振る舞いが壊れたら赤くなる装置」だが、ローカルで毎回手動 npm test を打たないと走らない。GitHub Actions に乗せると push のたびに勝手に走り、PR ページに緑/赤が表示される=これがセンサー

.github/workflows/test.yml を作る（20分）

  • 進級制作リポジトリのルートに .github/workflows/ ディレクトリを作り、その中に test.yml を新規作成
  • 進級制作が Node.js (npm) プロジェクトの場合の最小例（公式 quickstart に準拠）: 
    name: test

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
  • 進級制作が Python プロジェクトの場合の最小例: 
    name: test

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: pytest
  • agy に依頼する場合のプロンプト例: 
    @package.json （または @requirements.txt）を読んで、
push と pull_request トリガーで動く GitHub Actions の最小ワークフローを
.github/workflows/test.yml として作ってください。
- ubuntu-latest
- 公式 actions のメジャーバージョン v4 / v5 系を使う
- npm ci （または pip install -r requirements.txt）後に npm test （または pytest）
これ以外の steps は追加しないでください。
  • 新規ブランチに commit → push → GitHub の Pull requests → New PR で PR を作成 → Actions タブでワークフローが走るのを観察
  • 緑になった人は、2限前半で設定したブランチ保護の Require status checks に今走らせたワークフロー名（test）を追加して「テストが緑にならないと merge できない」状態を完成させる

赤になった場合の対処（5分・口頭）

  • Actions タブ → 該当 run → ログを開いて、どのステップで失敗したかを特定
  • ローカルでは通ったのに CI で落ちる典型: 依存ファイルが .gitignore 漏れで commit されていない / ローカルだけにある環境変数を CI で渡せていない / Node / Python のバージョン違い
  • 原因が掴めない場合は、agy にログを貼って「このCIエラーの原因と最小修正案を、ローカルの動作を変えずに提示して」と依頼。直接 commit を任せず、提案だけ受けて自分で適用
センサーは「赤くなった事実」が価値: GitHub Actions が赤くなることは「失敗」ではなく「振る舞いが変わったことを検出した」という成功イベント。本当に怖いのは、何も検出されないまま壊れたコードが main に merge されること。

2 限前半で有効化したブランチ保護ルールを編集して、今日 push した test ワークフローを 必須ステータスチェックとして登録。これで「テストが緑にならないと main に merge できない」状態が完成。Free private で UI に項目がない場合は、その旨を GEMINI.md に明記して規範運用に切り替える。
