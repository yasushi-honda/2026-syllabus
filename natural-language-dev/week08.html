この回のゴール

  • ハーネス＝「AI エージェントを長時間安全に走らせるための足場（ガイド＋センサー）」だと、自分の言葉で1〜2行で説明できる

  • Gemini CLI の BeforeTool Hook を1つ実装し、機密情報を含むコマンドを exit 2 で system block できる体験を積む
  • 「AI が触る前に止める（ガイド）」と「AI が触った後で検出する（センサー）」の両輪が揃って初めて、AI に長時間作業を任せられる感覚を掴む

第7回課題（TDD 1サイクル）の共有（10分）

  • 第7回で push した test: → feat: → refactor: の3コミットを、近くの人と互いに見せる
  • 家で2サイクル目以降を進めた人は、「テストが先に来ていたか」「Refactor で振る舞いが変わらなかったか」を1人1分で報告
  • よくある体感を共有: 「AI に任せたら関係ないファイルが書き換わった」「.env の中身を含むコマンドが履歴に残った」「テストはローカルでは通ったが他人の環境で落ちた」
  • 今日のテーマは、こうした事故を仕組みで防ぐ設計

「ハーネス」を公式定義で押さえる（15分）

  • 一次出典: Anthropic Engineering — "Harness design for long-running application development" から逐語:
    "A harness wraps the LLM with the additional tooling and infrastructure needed to deploy it for a specific task."
  • 翻訳の要点: ハーネス＝LLM を特定の仕事に投入するための周辺ツール・基盤の総称。LLM 単体ではなく、「LLM ＋ それを安全に走らせる足場」がひとつのシステム
  • 本授業での捉え方を2軸に整理:
    • ガイド（事前制御）: AI が触る前に「これはやるな・これを守れ」を伝える仕組み。GEMINI.md / .geminiignore / サンドボックス / ブランチ保護
    • センサー（事後検証）: AI が触った後で「振る舞いが壊れていないか」を検出する仕組み。GitHub Actions の test / lint / build / PR レビュー
  • 第7回で書いたテストは、それ単体ではローカルで走るだけ。今日の作業で GitHub Actions のセンサーとして PR ごとに毎回走る仕組みに昇格させる

今日のゴール提示（15分）

  • 進級制作リポジトリに次の3点を入れる:
    1. ガイドの1ファイル: .geminiignore（node_modules/ や .env* など AI に触らせない場所の宣言）
    2. センサーの1ワークフロー: .github/workflows/test.yml（push と PR で npm test 等が走る）
    3. Gemini CLI の BeforeTool Hook を1つ: .env を含む cat / echo 等のコマンドを exit 2 で system block
  • ブランチ保護の設定は GitHub の Settings から行うため、リポジトリ管理権限を持っていない人はペアの人と画面を共有して進める（自分のリポジトリでは家でも設定できる）
  • 本授業のグローバル方針（~/.claude/CLAUDE.md CRITICAL 節）でも「main / master ブランチへの直接 push は避ける」が MUST として書かれている。今日のブランチ保護はその仕組み化
今日の合言葉: 「AI を信用するために、AI を疑う仕組みを先に置く」。ガイドで触れる範囲を狭め、センサーで触った後を検出する。両輪が揃って初めて、長時間 AI に任せた作業の結果を信用できる。

ガイド（事前制御）— .geminiignore とブランチ保護

.geminiignore を作る（25分）

  • 一次出典: gemini-cli/docs/cli/gemini-ignore.md（公式）
  • 公式説明の要点（逐語に近い翻訳）:
    • 構文は .gitignore と同じ glob パターン（行末コメント・否定 ! ・ディレクトリ末尾の / 全対応）
    • 記述したファイルは @（ファイル参照）コマンドや read_many_files などのツール経由でアクセスできなくなる。Git からは普通に見える（.gitignore とは別物）
    • 変更を反映するにはセッションの再起動が必要
  • 進級制作リポジトリのルートに .geminiignore を新規作成し、最低限以下を入れる: 
    # 依存物・ビルド成果物
node_modules/
dist/
build/
.cache/

# 機密情報
.env
.env.*
*.pem
*.key
secrets/

# ローカル設定・履歴
.vscode/
.idea/
*.log
  • 進級制作で追加で AI に触らせたくない場所（例: 個人の調査メモ・本人写真・古い実験コード）があれば、自分の判断で1〜2行追記
  • commit して push。コミットメッセージは chore: add .geminiignore 等で短く

ブランチ保護を有効化（20分）

  • 一次出典: GitHub Docs ja — 保護されたブランチについて
  • 進級制作リポジトリの GitHub ページ → Settings → Branches → Add classic branch protection rule（または Rulesets）で main を対象に以下を最低限有効化:
    • Require a pull request before merging（PR 経由でないと merge できない）
    • Require status checks to pass before merging（後で作る GitHub Actions が緑になるまで merge できない／Actions が初回 push 後に「ステータスチェック候補」として選べるようになる）
  • これにより、AI が git push origin main を実行しても拒否される——「人間が PR をレビューする経路を物理的に必須化」する
  • リポジトリの可視性: Free プランの private リポジトリは branch protection の一部機能が使えない場合がある。Public リポジトリ・GitHub Pro・GitHub Team 以上では classic protection rule が利用可。Free private で設定できない場合は、規範として「main に直 push しない」を GEMINI.md に明記することで運用ルールに落とす

サンドボックスの話（5分・口頭）

  • 「サンドボックス」とは AI が実行するコマンドを本物のOS環境から隔離するレイヤー（Docker / VM / chroot 等）。Codespaces で開いていれば、それ自体がサンドボックスの一種
  • 今日は触らないが、本番リポジトリで Vibe Coding するときは「壊れていい環境」で動かすのが鉄則という認識を持つ
.geminiignore は .gitignore とは別: .gitignore は「Git にコミットしない」、.geminiignore は「Gemini CLI のツールから読まない」。役割が違うので、両方の管理が必要。.env は 両方に書く。
休憩 10分

センサー（事後検証）— GitHub Actions で第7回のテストを毎回走らせる

GitHub Actions の公式定義（10分）

  • 一次出典: GitHub Docs ja — GitHub Actions のクイック スタート
  • 要点: リポジトリのイベント（push / PR / schedule 等）をトリガーに、ワークフロー（YAML で定義した一連の処理）が自動実行される仕組み
  • ファイル配置: .github/workflows/<任意の名前>.yml。複数ファイル可
  • 本授業のテーマでの位置づけ: 第7回で書いたテストは「振る舞いが壊れたら赤くなる装置」だが、ローカルで毎回手動 npm test を打たないと走らない。GitHub Actions に乗せると push のたびに勝手に走り、PR ページに緑/赤が表示される=これがセンサー

.github/workflows/test.yml を作る（30分）

  • 進級制作リポジトリのルートに .github/workflows/ ディレクトリを作り、その中に test.yml を新規作成
  • 進級制作が Node.js (npm) プロジェクトの場合の最小例（公式 quickstart に準拠）: 
    name: test

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Node.js
        uses: actions/setup-node@v4
        with:
          node-version: '20'
          cache: 'npm'

      - name: Install dependencies
        run: npm ci

      - name: Run tests
        run: npm test
  • 進級制作が Python プロジェクトの場合の最小例: 
    name: test

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout
        uses: actions/checkout@v4

      - name: Setup Python
        uses: actions/setup-python@v5
        with:
          python-version: '3.12'

      - name: Install dependencies
        run: pip install -r requirements.txt

      - name: Run tests
        run: pytest
  • AI に依頼する場合のプロンプト例: 
    @package.json （または @requirements.txt）を読んで、
push と pull_request トリガーで動く GitHub Actions の最小ワークフローを
.github/workflows/test.yml として作ってください。
- ubuntu-latest
- 公式 actions のメジャーバージョン v4 / v5 系を使う
- npm ci （または pip install -r requirements.txt）後に npm test （または pytest）
これ以外の steps は追加しないでください。
  • 新規ブランチに commit → push → GitHub の Pull requests → New PR で PR を作成 → Actions タブでワークフローが走るのを観察
  • 緑になった人は、1限後半のブランチ保護の Require status checks に今走らせたワークフロー名（test）を追加して「テストが緑にならないと merge できない」状態を完成させる

赤になった場合の対処（10分）

  • Actions タブ → 該当 run → ログを開いて、どのステップで失敗したかを特定
  • ローカルでは通ったのに CI で落ちる典型: 依存ファイルが .gitignore 漏れで commit されていない / ローカルだけにある環境変数を CI で渡せていない / Node / Python のバージョン違い
  • 原因が掴めない場合は、AI にログを貼って「このCIエラーの原因と最小修正案を、ローカルの動作を変えずに提示して」と依頼。直接 commit を任せず、提案だけ受けて自分で適用
センサーは「赤くなった事実」が価値: GitHub Actions が赤くなることは「失敗」ではなく「振る舞いが変わったことを検出した」という成功イベント。本当に怖いのは、何も検出されないまま壊れたコードが main に merge されること。
2限 後半 約30分

Gemini CLI Hooks（BeforeTool / AfterTool）で機密情報コミット阻止

Hooks の公式仕様（10分）

  • 一次出典: gemini-cli/docs/hooks/reference.md（公式） / writing-hooks.md（公式）
  • Gemini CLI の Hook イベント（公式名・逐語）:
    • BeforeTool: ツールが実行される直前に発火（実行をブロックできる）
    • AfterTool: ツールが実行された直後に発火（結果を観察・ログ記録）
    • BeforeAgent / AfterAgent / BeforeToolSelection もある（今日は触らない）
  • 動作モデル:
    • Hook 本体は任意のシェルコマンド。stdin から JSON でイベント情報（ツール名・引数等）が入る
    • stdout に JSON を返すと Gemini CLI が解釈（後続を変える）。stderr はログとして保存
    • exit code 2 で system block: ツールの実行が止まり、AI 側にも「ブロックされた理由」が伝わる
  • ※ Claude Code には PreToolUse / PostToolUse という別綴りのイベントがある。Gemini CLI と Claude Code の Hook 用語は似ているが別物。設定ファイルも別。混同しない

機密情報コミット阻止 Hook を1つ書く（15分）

  • 狙い: AI が cat .env や echo $API_KEY のような機密情報を読みに行くコマンドを実行しようとしたとき、ツール実行前に止める
  • ~/.gemini/settings.json の hooks セクションに以下を追加（既存設定がある場合は hooks キーだけ merge）: 
    {
  "hooks": {
    "BeforeTool": [
      {
        "matcher": "Bash|run_shell_command",
        "command": "node ~/.gemini/hooks/block-secrets.js"
      }
    ]
  }
}
  • Hook 本体 ~/.gemini/hooks/block-secrets.js を新規作成: 
    #!/usr/bin/env node
// stdin から JSON を読む
let raw = '';
process.stdin.on('data', (chunk) => { raw += chunk; });
process.stdin.on('end', () => {
  const evt = JSON.parse(raw || '{}');
  const args = JSON.stringify(evt.tool_args || evt.params || {});
  // ブロック対象パターン（必要に応じて追加）
  const danger = /\.env\b|API_KEY|SECRET|PRIVATE_KEY|password|BEGIN [A-Z ]*PRIVATE KEY/i;
  if (danger.test(args)) {
    process.stderr.write('blocked: command references a secret-like token\n');
    process.exit(2); // ← system block
  }
  process.exit(0);
});
  • chmod +x ~/.gemini/hooks/block-secrets.js で実行権限を付与
  • 動作確認: Gemini CLI を起動 → 「.env の中身を見せて」と依頼 → ブロックされて AI 側に「blocked: command references a secret-like token」が伝わる。AI は別の方法（環境変数を直接読まない手順の提案など）に切り替えるはず
  • 注意: JSON スキーマ（フィールド名 tool_args / params 等）はバージョンで変わる可能性がある。動かなければ process.stderr.write(raw) で stdin の生 JSON を覗いて、実フィールド名に合わせる

AfterTool で監査ログを取る発展（5分・口頭）

  • AfterTool Hook を追加で書くと、AI が実行したすべてのコマンドと結果をローカルの監査ログ（例: ~/.gemini/audit.log）に追記できる
  • 家で発展課題に挑戦したい人は、stdin から tool_name / tool_args / result を取り出して append するだけの数行スクリプトを試すとよい
Hook の最強の防御は exit 2: stdout に JSON を返して「警告だけ」にすることもできるが、機密情報のように後から取り返しがつかない事象は exit 2 で system blockするのが筋。「人間判断を要求するシグナル」を必ず立てる。
