プロジェクト最終仕上げ②：ドキュメント整備・発表準備

Week 15 木曜 1・2限
テーマ
第14回で技術面を仕上げたので、本日は進級制作を他者に説明できる状態に整える。README整備、ADRの棚卸しと振り返り（なぜその判断をしたかを1本の物語にする）、そして次回（第16回）の成果発表に向けて「4月の自分のコード」と「前期末のコード」を比較する素材を整理する
キーワード
README整備 / ADR振り返り / 技術選択の根拠の言語化 / Before・After比較 / 発表構成 / 「プロンプト→コンテキスト→ハーネス」の進化
必要な準備
第14回完了（tech-debt.mdのP0解消・ADR-0004作成済み）／進級制作の4月時点のコード（git log の初期コミットや、第1回に振り返った当時のコード）にアクセスできる状態／これまで作成した全ADR（0001〜0004）を読み返せる状態

この回のゴール

  • 進級制作の README.md を、初めて見る人が読んでも動かせる状態（セットアップ手順・機能一覧・技術スタック）に書き直す
  • これまで作成したADR（0001〜0004）を通しで読み返し、「設計判断の連鎖」を1つの短い文章にまとめる
  • 4月時点の進級制作コードと前期末のコードを見比べ、変化点を3つ以上具体的に言語化する（機能・コードの質・AI活用の仕方のいずれでもよい）
  • 第16回の成果発表に向けて、発表の骨子（話す順番・見せる画面・所要時間の目安）を1枚のメモにまとめる

「動くコード」から「伝わる記録」へ

視点の切り替え: 第10〜14回は一貫して「仕様通りに動くか」「テストが緑か」「負債が減ったか」というコードそのものの品質を見てきた。本日は視点を変え、「自分以外の人がこのプロジェクトを理解できるか」を評価軸にする。README・ADR・発表資料は、コードと同じくらい責任あるコードの一部——自分が下した判断を他者が検証できる形で残すことも、AIと協働する開発者の責任の1つ。

授業の流れ

2コマ連続(90分 + 90分 = 計180分)。途中休憩あり。

1限 前半 約40分

なぜREADMEを書くか → 現状のREADMEを他人の目で読み直す

READMEの役割(15分)

  • READMEは「このプロジェクトを初めて開いた人が最初に読むドキュメント」。自分にとって当たり前の情報（セットアップ手順・使用言語・起動コマンド）ほど書き漏らしやすい
  • 本授業で最低限含める4項目: ①プロジェクトの概要（何をするアプリか）②セットアップ手順（Codespacesで開いてから動かすまでの手順）③機能一覧④使用した技術スタック（言語・ライブラリ・AI CLIの活用箇所）

現状のREADMEを他人の目で読み直す(25分)

  • 隣の人とリポジトリを見せ合い、相手のREADMEだけを見て「どうやってこのアプリを動かすか」を1分で説明できるか試す。説明できなければ、その部分がREADMEに不足している証拠
  • 指摘を受けた項目をメモしておき、1限後半の書き直しに反映する
今日の視点: 「自分は分かっている」と「初めて読む人にも伝わる」は別の基準。他人に読んでもらって初めて見つかる不足がある。
1限 後半 約50分

README を書き直す

README書き直し(45分)

  • 1限前半で受けた指摘と、4項目のテンプレートを元に README.md を書き直す
  • agy への指示例（ゼロから作る場合と、既存を直す場合の両方に使える）: 
    このリポジトリの README.md を、初めて見る人でも
セットアップから起動までできる内容に書き直してください。
含めてほしい項目:
1. プロジェクトの概要（1〜2文）
2. セットアップ手順（Codespacesで開いてからの具体的なコマンド）
3. 主な機能一覧（箇条書き）
4. 使用技術スタック（言語・主要ライブラリ・活用したAI CLI）

package.json と src/ の構成を見て、実態と合っているか
確認しながら書いてください。
  • agyが生成した内容を鵜呑みにせず、実際にセットアップ手順通りに1度動かしてみて、コマンドが実態と合っているか自分で確認する（第4回で学んだ「AIの出力のブレを体感する」姿勢と同じ）

相互レビュー(5分)

  • 書き直したREADMEをもう一度隣の人に見せ、1限前半より説明しやすくなったか確認する
休憩 10分
2限 前半 約50分

ADRを通しで振り返る → 4月と前期末のコードを比較する

ADRの振り返り(20分)

  • これまで作成したADR（第10回0001〜第14回0004）を通しで読み返す
  • 各ADRのDecision（何を決めたか）だけを抜き出し、時系列で並べる。「設計判断がどうつながっているか」の連鎖が見えるはず
  • 1つのドキュメント（例: docs/adr-summary.md）に、ADR番号・決めたこと・理由を1行ずつまとめる

4月と前期末のコードを比較する(30分)

  • 第1回で振り返った「4月時点のコード」を git log で開き直し、前期末の現在のコードと見比べる
  • 変化点を3つ以上、具体的に書き出す。観点の例:
    • 機能面: 何が新しくできるようになったか
    • コードの質: テストの有無、命名、関数分割の変化
    • AI活用の仕方: 第1回のVibe Codingと、第10〜14回のSDD（仕様→計画→実装→検証）では、AIへの指示の出し方がどう変わったか
  • agy への指示例: 
    git log --oneline の最初の10件と直近10件を比較して、
ファイル構成・依存パッケージ・テストの有無にどんな
違いがあるか要約してください。断定はせず、
「〜が増えている」「〜が新しく追加されている」という
観察ベースで教えてください。
2限 後半 約30分

発表の骨子を作る

発表構成メモの作成(30分)

  • 第16回の成果発表（1人あたりの持ち時間は当日案内）に向けて、以下を1枚のメモにまとめる:
    1. 話す順番: 概要 → 技術選択の根拠（ADR振り返りより）→ Before/After比較 → AI活用プロセスで工夫した点 → 今後の課題
    2. 見せる画面: デモで動かす画面、見せるコードの箇所、READMEのどこを見せるか
    3. 所要時間の目安: 各項目に何分使うか
  • 隣の人とメモを見せ合い、「分かりにくそうな箇所」を1つずつ指摘し合う
発表は準備で9割決まる: 当日にぶっつけ本番で話すのではなく、本日作った骨子メモを見ながら1回は声に出して練習しておくと、第16回当日の緊張が下がる。
まとめ 約10分

振り返り＆次回予告

  • 今日のキーワード: README整備 / docs/adr-summary.md / ADRの連鎖 / Before・After比較 / 発表骨子メモ
  • 覚えてほしいこと:
    • コードの品質と伝わる記録は別の能力。両方揃って初めて「公開できる」状態になる
    • ADRを振り返ると、バラバラに見えた各回の判断が1つの筋の通ったストーリーになっていることに気づける
  • 「責任あるコード」第6の具体例: README・ADR振り返りを通じて自分の判断を他者が検証できる形にした＝「動くコードを、説明できるコードに変える責任」
  • 次回（第16回・最終回）: 成果発表＆総括。「4月の進級制作」と「前期末の進級制作」を比較する成果発表。前期の振り返り：「プロンプト→コンテキスト→ハーネス」の進化を実感。後期への接続
  • 家での発展（任意）: 発表骨子メモを見ながら1回声に出して練習する／READMEをもう一度他の人に読んでもらいフィードバックをもらう
