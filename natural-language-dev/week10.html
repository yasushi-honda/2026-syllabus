この回のゴール

  • 第6回の SDDサイクル「Spec → Plan → Tasks → Implement」（Spec Kit 公式 docs より）の前半3つ——Spec → Plan → Tasks——を、進級制作の本気の機能追加を題材に1周回しきる
  • 第5回の PRD（要求の意図）と Spec Kit の spec.md（受け入れ基準）の役割分担を、自分の機能を例に1〜2行で説明できる
  • ADR（Architectural Decision Record）を「重要設計判断 1 つ」について書き、「決めたこと／背景／なぜ他を採らなかったか／結果（trade-off）」の4節を埋めることができる（参考: Architectural Decision Records = ADR エコシステムのハブ）
  • テスト計画を Definition of Done（完成の定義）として書き、「これが緑になれば完成」を spec.md の受け入れ基準とリンクできる
  • /speckit.tasks が生成した tasks.md を GitHub Issue に分解し、GitHub Project（テーブル or ボード）に並べて「次に何をやるか」を1画面で見られる状態にする
  • 第11回（実装）で TDD サイクルを回す準備として、tasks の各行が「30〜60分で終わるサイズ」「テストが先に書ける粒度」になっていることを確認できる

SDD 実践プロジェクトの全体像（Week10 → 11 → 12）

3週連続プロジェクト: 本日（第10回 設計）→ 第11回 実装（TDDサイクル＋MCP連携）→ 第12回 検証と改善（テスト結果分析＋リファクタリング）の3回で、進級制作に1つ「本気の機能」を追加しきる。今日の spec.md / ADR / tasks.md / GitHub Project が翌週以降の「正本」になる。今日設計を雑にすると2週間引きずる——焦らず時間を使う。

ADR を1本書く(20分)

  • plan.md の中から「重要な設計判断」を1つ選ぶ(複数あれば後回しでOK、今日は1本を完成させる)。例:
    • 「React に移行するか、素の JS のまま進めるか」
    • 「Leaflet にするか、Mapbox / Google Maps にするか」
    • 「店舗データを localStorage に置くか、JSON ファイルとして配信するか」
    • 「テストランナーを vitest にするか、Jest にするか」
  • ADR(Architectural Decision Record)とは: 「単一の設計判断と、その根拠を記録する文書」(adr.github.io 公式: "An Architectural Decision Record (ADR) captures a single AD and its rationale; Put it simply, ADR can help you understand the reasons for a chosen architectural decision, along with its trade-offs and consequences.")
  • 本授業で採用するテンプレート: Michael Nygard 形式(2011年 "Documenting Architecture Decisions" で提唱、ADR エコシステムで最広く使われている形式)。Joel Parker Henderson の ADR examples リポジトリに多数の参考実装あり
  • ファイル配置: docs/adr/0001-<decision-slug>.md(連番 + 短い slug)。最低限の4節構成: 
    # 0001. Leaflet を採用する(Mapbox / Google Maps ではなく)

## ステータス
Accepted (2026-XX-XX)

## 背景 (Context)
進級制作に地図表示機能を追加する必要がある。候補は3つ:
Leaflet (OSS / OpenStreetMap)、Mapbox (商用 / 無料枠あり)、
Google Maps Platform (商用 / 無料枠 $200/月相当)。

## 決定 (Decision)
Leaflet 1.9.4 + OpenStreetMap タイルを採用する。

## 理由・なぜ他を採らなかったか
- 登録手続き・API key 不要(授業時間内に実装に着手できる)
- 商用ライセンスの心配がない (OSS / BSD-2)
- 第9回で最小実装の動作確認済み
- Mapbox / Google は将来のスケール時に再評価する(別 ADR で)

## 結果・trade-off (Consequences)
- OSM タイルは商用利用時に attribution 表示が必須
- ベクタータイルや高度なスタイルが必要になったら Mapbox 再評価
- 1日あたりのタイル取得量に注意 (OSM タイル利用規約)
  • ADR は agy に下書きさせて OK。ただし「なぜ他を採らなかったか」「trade-off」は自分の言葉で必ず推敲する(ここが ADR の価値の本体)

    ## Definition of Done

このスコープが完成したと言えるのは、以下が全て満たされたとき:

- [ ] 受け入れ基準 1〜3 に対応する vitest テストが存在し、全て緑

spec.md / plan.md / ADR / DoD の関係: spec.md は「何が動けば完成か(WHAT)」、plan.md は「どう作るか(HOW)」、ADR は「なぜそう決めたか(WHY)」、DoD は「緑になる条件のリスト」。来週(第11回)実装に入った自分が迷ったら、この4つを順に読み返す。

/speckit.tasks で tasks.md を生成(10分)

  • /speckit.tasks を呼ぶと、Spec Kit は plan.md を読んで 実行可能なタスク一覧(tasks.md)を生成する
  • レビュー観点(第6回からの再確認):
    • 仕様の受け入れ基準と1対1で紐づくタスクがあるか(漏れチェック)
    • 1タスクの粒度が「30〜60分で終わりそう」か(大きすぎるタスクは分割を agy に依頼)
    • テストを先に書けるタスクか(第7回 TDD で Red → Green → Refactor を回せる粒度か)
    • 依存関係が見えるか(タスク A が終わらないと B に着手できない、等)
  • 5〜10件の Issue 候補が並んでいれば適切なサイズ。15件以上なら分割しすぎ、3件以下なら粒度が大きすぎる

tasks.md を GitHub Issue に分解(10分)

  • tasks.md の各行を GitHub Issue として作成する。gh CLI(Codespaces には標準で入っている)を使うと一括で楽: 
    # 1件ずつ作る例
gh issue create \
  --title "[feat] 地図画面のルーティングを追加 (#1/8)" \
  --body "$(cat <<'EOF'
spec.md 受け入れ基準 1 に対応。
src/pages/map.html を新規作成、src/main.js のルーターに /map を追加。
完了条件: vitest の routing.test.js が緑、ブラウザで /map に遷移できる。
EOF
)" \
  --label "feat,spec-kit"
  • Issue タイトルに spec.md の受け入れ基準番号を含めると追跡しやすい
  • Issue 本文には「完了条件」(DoD の該当行を引用)を必ず入れる
  • 講師から事前に渡された個人 access の都合で Free private のリポジトリでも gh issue create は動作するはず。ハマったら GitHub Web UI から手動でも OK

GitHub Project にまとめる(10分)

  • 一次出典: GitHub Docs ja — Projects の について。Projects は適応性のあるテーブル・ボード・ロードマップの3レイアウトで作業を視覚化するツール(公式 docs より)
  • GitHub Web UI で 進級制作リポジトリ → Projects タブ → New project → テンプレート「Board」を選択 → 名前を「<機能名> SDD」のように付ける
  • 作成した Issue 群を Project に追加(Project の画面で + ボタン → リポジトリの Issue を選択 / または各 Issue の右サイドバー「Projects」セクションから追加)
  • カラム構成は最小限で OK: Todo / In progress / Done。慣れたら「Blocked」「Review」を増やす
  • 今日の最後の状態として、Todo カラムに全 Issue が並んでいる状態を作る。これが第11回の出発点になる
Project は「次に何をやるか」を1画面で見るためのもの: Issue を作るだけだと一覧が長くなって埋もれる。Board に並べると「Todo に何枚あるか」「In progress に何枚詰んでいるか」が即座に見える。第11回の冒頭でこの Board を開いて1枚 In progress に移すところから始める。
