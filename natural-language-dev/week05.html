PRDとADRで「なぜそうしたか」をAIに渡す

Week 5 木曜 1・2限
テーマ
GEMINI.md（指示）に加えて、PRD（要求の意図）と ADR（判断の理由）を書き、Memory Import と Plan Mode で AI に渡す
キーワード
PRD / ADR / Memory Import（@file.md）/ Plan Mode / 責任あるコード
必要な準備
第4回完了（GEMINI.md の初版がリポジトリにある／docs/vibe-before-after.md 提出済み）・進級制作リポジトリが Codespaces で開ける状態

この回のゴール

  • GEMINI.md だけでは表現しづらい 「なぜその要求か」「なぜその設計を選んだか」 を、PRD と ADR という形で書き分けられる
  • 進級制作の小機能 1 つについて、最小の PRD（要求仕様書）と ADR（設計判断記録）を書ける
  • GEMINI.md に @docs/prd/... @docs/adr/... を書いて、Memory Import Processor で PRD/ADR を AI が毎回読む状態を作れる
  • Gemini CLI の Plan Mode を起動し、PRD を起点とした実装計画を AI に立てさせ、人間がレビューできる
  • 「指示（GEMINI.md）」「意図（PRD）」「判断（ADR）」「計画（Plan Mode）」の 4 階層が、「責任あるコード」を支える文書セットであることを体感する

授業の流れ

2コマ連続（90分 + 90分 = 計180分）。途中休憩あり。

1限 前半 約40分

前回の振り返り＆GEMINI.md だけでは届かないこと

第4回課題の共有（10分）

  • GEMINI.md 初版と docs/vibe-before-after.md から、「After で改善した点」「After でも変わらなかった点」を 1 つずつ口頭共有
  • 家で「効かなかった指示を 1 行追記」を試した人がいれば、その追記内容と再実行結果を共有

「GEMINI.md に書きにくいこと」を出し合う（15分）

  • GEMINI.md はあくまで 「AI への指示文」。次のような情報は書きにくい・書いても効かない:
    • 「なぜこの機能が必要なのか」（要求の背景）
    • 「誰のために作っているのか」（対象ユーザー）
    • 「他にも案 A・案 B があったが、なぜ案 C を選んだのか」（設計判断の理由）
    • 「これは意図的にやっていない」（非ゴール）
  • これらは AI への指示というより「人間が後から読み返すための意図と判断の記録」。AI は副産物として読めるが、本来は未来の自分とチームメイトに向けて書く文書
  • 業界では古くから 2 種類のフォーマットが定着している:
    • PRD（Product Requirements Document：製品要求仕様書）= 「何を、なぜ、誰のために」を書く
    • ADR（Architecture Decision Record：アーキテクチャ決定記録）= 「どう作るか、なぜその選択にしたか」を書く

今日のゴール提示（15分）

  • 今日は進級制作の小機能 1 つを題材に、PRD（1 限後半）と ADR（2 限前半）を 1 本ずつ書く。AI と協働で書き、人間がレビュー・編集する
  • 書いた PRD/ADR を GEMINI.md から @docs/prd/... @docs/adr/... 構文で取り込ませる（Gemini CLI 公式の Memory Import Processor）。これで AI は毎プロンプトで PRD/ADR まで読み込んだ状態で答える
  • 仕上げに Plan Mode（Gemini CLI の読み取り専用設計モード。公式: "a read-only environment for architecting robust solutions before implementation"）で、PRD を起点に実装計画を AI に立てさせ、計画 markdown を読み返す
  • これにより、4 階層が揃う:
    1. 指示: GEMINI.md（第4回で作成）
    2. 意図: PRD（今日 1 限後半）
    3. 判断: ADR（今日 2 限前半）
    4. 計画: Plan Mode の出力 markdown（今日 2 限後半）
  • 通年テーマ 「責任あるコード」 の中心装置: 「動けばいい」で終わらせず、なぜそう動かすかを書き残す
今日の合言葉: 「GEMINI.md は AI への指示書／PRD・ADR は未来の自分への申し送り」。両方を書いて、両方を AI に読ませます。
1限 後半 約50分

PRD（要求の意図）を AI と一緒に書く

題材を 1 つ決める（5分）

  • 進級制作に追加したい 小機能 1 つ を選ぶ。サイズ感は「2〜3 時間あれば実装できそう」程度。例:
    • お問い合わせフォームに「ファイル添付」機能を追加
    • 記事一覧に「タグで絞り込み」機能を追加
    • マイページに「編集履歴の表示」を追加
    • ダーク/ライトテーマ切替を追加
  • 第8回「ハーネスエンジニアリング入門」、第10回「SDD実践プロジェクト①」でも使い回せる題材だと、後の回が楽になる

PRD の最小構成を理解する（5分）

  • 業界には決定版テンプレートはなく、長すぎないことが一番大事。今日は次の 5 セクションだけで書く: 
    # PRD: ＜機能名＞

## 1. 背景
（なぜ今これが必要か。1〜3 行）

## 2. 対象ユーザー
（誰がこの機能を使うか。1〜2 行）

## 3. 成功基準
- 達成できたと判定できる、観測可能な条件を 2〜4 個

## 4. 非ゴール（やらないこと）
- 今回は意図的にやらないことを 1〜3 個

## 5. 想定リスク・前提
（書ける範囲で 1〜2 行）
  • 3 と 4 が要。「成功基準」を観測可能に書けるか、「やらないこと」を明示できるかが PRD の腕の見せ所

AI にドラフトを作らせる（15分）

  • Gemini CLI を起動し、たとえばこう頼む: 
    ＜機能名＞ という機能を進級制作に追加したい。
PRD のドラフトを書いてほしい。
セクションは「背景／対象ユーザー／成功基準／非ゴール／想定リスク」の5つ。
各セクションは1〜3行で簡潔に。
不明な点は私に質問してから書いてください。
  • 「不明な点は質問してから書いて」がポイント。これを書かないと AI は勝手に前提を埋めてしまう
  • AI からの質問に答えながら、ドラフトを生成させる

人間がレビュー・編集する（20分）

  • AI が作ったドラフトをそのまま採用しない。「自分が書きたかったこと」と違う部分を必ず直す。AI は世間一般的な PRD を書きがちで、自分の進級制作の文脈を取りこぼす
  • 特にチェックする観点:
    • 背景: 「なぜ自分はこれを作りたいのか」が自分の言葉で書かれているか
    • 成功基準: 「動けばいい」で終わっていないか。「ファイルが 5MB まで添付できる」「タグで絞ると該当記事のみ表示される」など観測可能な条件になっているか
    • 非ゴール: 1 つでいいので明示する。「画像のサムネイル生成は今回はやらない」など。これがあると AI が暴走しにくい
  • 進級制作リポジトリに docs/prd/ ディレクトリを作って docs/prd/<feature-slug>.md として保存

記録（5分）

  • git add docs/prd/<feature-slug>.md（commit はあとで PRD・ADR・GEMINI.md 更新をまとめて行う）
書きすぎないコツ: PRD は 1 画面に収まる長さを目標に。長くなったら「自分が大事だと思う 5 行」だけ残して残りを削る。長い PRD は自分も AI も読まなくなります。
休憩 10分
2限 前半 約50分

ADR（設計判断）を書く＋ Memory Import で AI に取り込ませる

ADR の最小構成（5分）

  • ADR は Michael Nygard が 2011 年のブログ記事 Documenting Architecture Decisions で提唱した形式が広く使われている。今日は最小限で書く: 
    # ADR-0001: ＜設計判断のタイトル＞

## ステータス
提案 / 採用 / 却下 のどれか

## コンテキスト
（どういう状況で、何を判断する必要があったか。2〜4 行）

## 決定
（最終的に何を選んだか。1〜2 行）

## 結果（影響）
（この決定によって何が起きるか。良い影響と悪い影響を両方。2〜4 行）

## 検討した代替案
- 案 A: なぜ選ばなかったか（1 行）
- 案 B: なぜ選ばなかったか（1 行）
  • 「検討した代替案」こそ ADR の核。「他の選択肢と比べたうえでこれを選んだ」という判断のプロセスを残すのが目的

1 限後半の PRD から「設計判断ポイント」を 1 つ抽出（5分）

  • 1 限後半で書いた PRD に対して、実装で判断が必要になりそうなポイントを 1 つ選ぶ。例:
    • ファイル添付 → 「保存先は ローカル / クラウドストレージ / DB バイナリ のどれにするか」
    • タグ絞り込み → 「タグの管理は 文字列カラム / 中間テーブル / NoSQL のどれにするか」
    • テーマ切替 → 「設定の保存先は localStorage / Cookie / サーバ DB のどれにするか」

AI と「なぜを 5 回問う」役割分担で書く（20分）

  • Gemini CLI に次のように頼む: 
    これから ADR を書きます。
題材は「＜設計判断ポイント＞」です。
あなたは「なぜ？」を5回繰り返す質問役をしてください。
私が答えるたびに、もう一段深い「なぜ？」を返してください。
5 回終わったら、その対話を ADR の「コンテキスト」と「決定」と「検討した代替案」に整形してください。
  • AI と対話しながら、自分の中で暗黙だった判断基準を言語化する。これが ADR の本来の価値
  • 仕上げ: AI が整形したドラフトに、自分の言葉で「結果（影響）」セクションを書き足す（AI には書けない、自分のプロジェクト固有の影響）
  • 進級制作リポジトリの docs/adr/0001-<slug>.md として保存

Memory Import で GEMINI.md から PRD/ADR を取り込む（15分）

  • Gemini CLI 公式の Memory Import Processor を使う。GEMINI.md 内に @<file> と書くと、その内容が連結時に展開される（公式: "Use the @ symbol followed by the path to the file you want to import"）
  • 第4回で作った GEMINI.md の末尾に次のような行を追加: 
    ## 進行中の機能の意図と判断
@./docs/prd/<feature-slug>.md
@./docs/adr/0001-<slug>.md
  • Gemini CLI 上で /memory reload（または再起動）→ /memory show でPRD と ADR の中身が AI に渡される指示文に含まれているか確認
  • これで AI は毎プロンプトで「指示（GEMINI.md 本体）＋ 意図（PRD）＋ 判断（ADR）」を読んでから応答する状態になる
  • 公式ベストプラクティス（Memory Import）からの注意:
    • 相対パスを優先する（移植性）
    • import チェーンを浅く保つ（深くネストしない）
    • 参照ファイルが存在することを確認
    ※公式仕様として、import 深さの既定上限は 5 階層、循環参照は自動で検出される

ステージング（5分）

  • git add docs/adr/ docs/prd/ GEMINI.md しておく（commit はまとめて 2 限後半 or まとめパートで）
ADR が複数になったら: ファイル名は 0001-, 0002- と番号をつけて時系列管理。GEMINI.md から @./docs/adr/ 配下を1つずつ参照すると、AI が「過去にこれを決めた」を覚えてくれます。
2限 後半 約30分

Plan Mode で「PRD を読んだうえでの実装計画」を立てさせる

Plan Mode の使い方（5分）

  • 公式: Plan Mode は "a read-only environment for architecting robust solutions before implementation"（実装前に堅実な解法を設計する読み取り専用環境）
  • Gemini CLI 起動中に Plan Mode に入る方法は主に次の 4 通り（公式）:
    • (a) Shift+Tab で approval mode を循環させる
    • (b) /plan ＜目標＞ をプロンプトで実行（＜目標＞ は省略可）
    • (c) 自然言語で "start a plan for ..." のように依頼する
    • (d) 起動時に gemini --approval-mode=plan を指定
  • 授業では (b) を使う（一番分かりやすい）

PRD を起点に実装計画を立てさせる（15分）

  • 2 限前半で GEMINI.md から PRD/ADR を取り込んだ状態のまま、Gemini CLI で次のように依頼: 
    /plan PRDで定義した機能を実装するための計画を立ててください。ADR の決定事項に沿って進めてください。
  • Plan Mode はファイルを変更せず、計画 markdown を生成する
  • 計画は Ctrl+X で外部エディタ（$EDITOR で指定したエディタ。Codespaces では既定で vim 等）に開いて直接編集できる（公式）。気になる箇所はその場でコメント追記

計画 markdown をレビューする（10分）

  • 3 つの観点で計画を読む:
    • PRD の成功基準が漏れなく計画に反映されているか（PRD § 3 の 2〜4 個の条件すべてに対応するステップがあるか）
    • PRD の非ゴールに踏み込んでいないか（「やらない」と書いたものが計画に紛れ込んでいないか）
    • ADR の決定事項に沿っているか（採用した案が反映されているか・却下した案が紛れ込んでいないか）
  • 気になる点があれば、Plan Mode 内で追加の指示を投げて計画を更新させる（実装はまだしない）
  • 納得できたら計画 markdown を docs/plans/0001-<feature-slug>.md として保存
  • commit: git add docs/ GEMINI.md && git commit -m "PRD/ADR/Plan を整備し GEMINI.md から取り込み"
実装は来週以降: 今日は 計画まで で止める。Plan Mode から抜けて実装してしまうと「PRD/ADR を書いた価値」を実感する前に手が動いてしまいます。
まとめ 約10分

振り返り＆次回予告

  • 今日のキーワード: PRD / ADR / Memory Import（@file.md）/ Plan Mode / 4 階層の文書セット
  • 覚えてほしいこと: 「指示（GEMINI.md）」「意図（PRD）」「判断（ADR）」「計画（Plan Mode 出力）」が揃うと、自分も AI も同じ前提で動ける。これが「責任あるコード」の最小フォーマット
  • 次回（第6回）: Spec-Driven Development（SDD）入門。今日書いた PRD/ADR/計画は、SDD でいう「仕様」が実行可能な成果物になる素材。GitHub Spec Kit の概念と Gemini CLI / Copilot CLI の Plan Mode 比較を扱う
  • 家での発展（任意）: 今日 GEMINI.md に追加した @ import 行を、ADR が増えたら 1 行ずつ足してみる。3 個目あたりで「GEMINI.md 本体は方針、詳細は ADR に分ける」分業が見えてくる

課題・次回までにやること

必須
PRD と ADR を 1 本ずつ push

進級制作リポジトリに docs/prd/<feature-slug>.md と docs/adr/0001-<slug>.md を作成して push。それぞれの最小セクション（PRD: 5 セクション／ADR: 5 セクション）が埋まっていればよい。1 画面に収まる長さに留めること。

必須
GEMINI.md から PRD/ADR を @ import

第4回で作った GEMINI.md の末尾に @./docs/prd/... と @./docs/adr/... を 1 行ずつ追加。/memory show で取り込みを確認したスクショ or テキスト出力をあわせて push（任意の docs/memory-show.txt など）。

必須
Plan Mode の出力 markdown を push

Plan Mode に立てさせた計画を docs/plans/0001-<feature-slug>.md として保存。PRD § 3「成功基準」の各項目に対応する計画ステップが入っていることを目視確認。

推奨
ADR を 1 本追加（別の判断ポイントで）

授業中に書いた ADR-0001 とは別の設計判断ポイントを 1 つ取り上げ、ADR-0002 として書いてみる。「2 本目を書くと『1 本目の書き方』が見えてくる」のが ADR の特徴。

推奨
計画通りに実装してみる

Plan Mode を抜けて、計画 markdown のステップに従って実装を進めてみる。途中で計画と現実がズレたら、PRD/ADR/計画のどれを直すべきかを意識する（→ 第6回 SDD で扱う本題）。
