テスト結果を 3 軸で読み直す → Green を維持したままリファクタリング

テストを 3 軸で読み直す(20分)

  • Green だけを見て「品質 OK」と判断しないための 3 軸:
    1. Coverage（実行された行の割合）: vitest なら npm test -- --coverage または vitest run --coverage（プロジェクトの package.json スクリプト依存）で計測。表示された行カバレッジ・分岐カバレッジのうち50% を切っている領域があれば、そこは「テストがない = 変更が壊しやすい」領域
    2. .skip / .todo: grep -rn "\.skip\|\.todo" src/ で棚卸し。意図がある skip（例: 実装が第13回以降）と、惰性の skip（Green にする過程で赤いテストを黙らせた）を分ける。惰性の skip は今日中に直すか、tech-debt.md に登録する
    3. 直近の失敗テスト / フレーク: GitHub Actions の test.yml の直近 5〜10 実行を見て、同じコードで色が変わっているテストがないか確認。フレークが 1 件でもあれば tech-debt.md に登録（「T-XXX テスト routing.test.js フレーク疑い、直近 5 実行のうち 1 回赤」）
  • agy に対する指示例: 
    @src/__tests__/ 以下の .skip / .todo をすべて列挙してください。
それぞれについて「なぜ skip されているか」の推測を、
コミットログ (git log -p) と直近の PR コメントから根拠付きで教えてください。

Green を維持したままリファクタリング(30分)

  • 本日のリファクタは Green 維持が絶対条件。1 変更ごとに npm test を回して、色が変わらないことを確認しながら進める
  • スコープを絞る（本日中に全部直そうとしない）:
    • 命名だけ（変数名・関数名・ファイル名の 1〜3 箇所）
    • 関数分割（30 行超えの関数を 2〜3 個に割る）
    • 重複削除（3 回以上出てくるコピペを 1 つに集約）
  • agy に頼むときの指示（Green 維持を明示するのがコツ）: 
    src/pages/map.js の handleClick 関数を、
以下の観点で読みやすくリファクタしてください:
- 責務が 2 つに見える → 関数を 2 つに分割
- マジックナンバー 3.14 を定数化

制約:
- src/__tests__/routing.test.js の Green を維持すること
- 分割後の関数名は動詞始まりの英語
- 分割後、npm test の結果を貼って Green を確認してから止まってください
  • 1 リファクタごとに 1 commit（refactor: extract handleClick into ...）。意味のない Refactor（コード形状は変わったが読みやすさに寄与しない）を消すために、コミット単位で自己レビューして「1 分で説明できる Refactor か」を確認
  • Refactor だけの PR を出す（refactor/<area>-<short-slug> ブランチ）: 
    git checkout main && git pull
git checkout -b refactor/map-page-cleanup
# ...Refactor commits...
git push -u origin refactor/map-page-cleanup
gh pr create --title "refactor: map ページの命名と分割整理" --body "..."
  • Refactor 中に「Green を維持できないほど大きな変更」に見えたら、その場でやめる。それは本当は Refactor ではなく設計変更。ADR-0002 に判断を書き、tech-debt.md に「T-XXX <area> の設計変更検討」として登録して先送りする
「Refactor が壊れるとき」の分岐点: Green を維持できないリファクタは、多くの場合 そのテストがそもそも実装詳細にべったりだったことのシグナル。ここで「実装に合わせてテストを書き換える」のはアンチパターン（テストが仕様を担保しなくなる）。テスト自体の書き直しが必要なら、それは別 PR・別 Issueとして立て、spec.md の受け入れ基準に戻って「何を確認するテストだったか」から書き直す。

技術的負債とは何か(10分)

  • 1 行の定義（本授業で使う共通理解）: 「今すぐは直さないと決めた、あとで直す必要のある課題」。隠す（気付かないふりをする）でも、過剰対応する（今すぐ全部直そうとしてリリースが止まる）でもなく、可視化して先送りするのが技術的負債の扱い方
  • 本授業での典型的な発生源（進級制作でよく出るもの）:
    • Refactor したかったが Green 維持できず途中で止めたコード
    • .skip / .todo のまま残っているテスト

    • /speckit.analyze で検出したが今日直さないと決めた差異

セキュリティ観点でのコードチェック — Secret scanning + Dependabot + npm audit + OWASP Top 10

GitHub の Security タブを見る(10分)

  • 各自のリポジトリで Security タブを開く（https://github.com/<user>/<repo>/security）
  • シークレット スキャン(公式名: Secret scanning): Public リポジトリでは既定で有効。API キー / トークン / 秘密鍵が commit に混入すると自動検知する。GitHub Docs 公式: 「シークレット スキャンは、パートナーの一覧および独自パターンに一致するシークレットについて、リポジトリ全体をスキャンします」。検知メールは commit した本人と管理者に届く
  • 今日確認する:
    • Secret scanning alerts の一覧に過去に混入した秘密がないか（授業中に .env を誤 push した / API キーをコード直書きした等）
    • アラートがあれば、キーの無効化 → 再発行 → コードから削除 → history からも消去の 4 手が必要。history の消去は git filter-repo（GitHub 公式が推奨、旧 git filter-branch の後継）や BFG Repo-Cleaner を使う。git rebase -i は直近コミットの整形用で、全 history にまたがる秘密削除には設計上不足なので使わない。今日は「存在の確認」までで OK（対応は次回以降 or 家で）
  • Dependabot alerts: 依存パッケージ（package.json 等）のバージョンに既知の脆弱性が見つかると自動で Issue 状の警告が出る。GitHub Docs 公式: 「Dependabot alerts は、依存関係の脆弱性についてユーザーに通知します」。公式 docs は「リポジトリ管理者や organization オーナーが有効化する」と説明しており、進級制作リポジトリで未有効の人は Security タブ → Dependabot alerts の Enable ボタンを押して今日オンにする（Public リポジトリなら無料）
  • 今日確認する:
    • Dependabot alerts が何件出ているか
    • Severity（重大度）が Critical / High のものが 1 件でもあれば tech-debt.md に P0 で登録
    • Dependabot は自動 PR で修正案を出せる（設定で有効化）。今日は「そういう機能があると認識する」までで OK

Node プロジェクトなら npm audit(10分)

  • 進級制作が Node（package.json あり）を使うプロジェクトなら、ローカルで実行: 
    npm audit
  • npm docs 公式（npm-audit）: 「プロジェクトで構成されている依存関係の説明をレジストリに送信し、既知の脆弱性のレポートを要求する」。npm audit fix で自動修正が試みられるが、breaking change を含む場合は手動で package.json のバージョンを上げる必要がある
  • 本日の運用:
    • Critical / High の指摘: tech-debt.md に P0 か P1 で登録し、可能なら npm audit fix を試す。fix 後は 必ず npm test で Green を再確認（依存バージョンアップが挙動を変えることがある）
    • Moderate / Low: tech-debt.md に P2 で登録、今日は手を付けない
  • Node を使わないプロジェクト（バニラ HTML/CSS/JS のみ、Python 単体等）の場合は npm audit はスキップし、代わりに pip-audit（Python）や、依存の ロックファイルの日付を見て「1 年以上更新していない依存があれば tech-debt.md に登録」で代替
