この回のゴール

  • 第10回で生成した tasks.md の各タスクを、TDD サイクル（Red → Green → Refactor）で 1 枚ずつ Green に変えていく流れを 1 周体験する
  • /speckit.analyze（仕様・計画・タスクの整合性チェック）を /speckit.implement 前に走らせる運用習慣を作る（Spec Kit 公式: "For production features with meaningful ambiguity, run /speckit.analyze before /speckit.implement to check spec/plan/task consistency"）
  • Antigravity CLI の /mcp で MCP（Model Context Protocol）サーバーを 1 つ接続し、agy に「外部ツールに繋がる手」を与える体験を持つ（GitHub MCP / Filesystem MCP / Web Fetch MCP のいずれか 1 つを講師が事前検証済みの最小構成で配布）
  • ハーネスによる品質チェックの考え方（Anthropic Engineering "Harness design for long-running application development" 由来）を、自分のリポジトリの test.yml（事前制御）+ コードレビュー（事後制御）と対応付けて 1〜2 行で説明できる
  • GitHub Flow（公式 6 ステップ: ①分岐を作成 ②変更を加える ③pull request を作成 ④レビューコメントに対処 ⑤pull request をマージ ⑥ブランチを削除）を 1 タスク分で 1 周完走する（feature ブランチ → push → PR → セルフレビュー or ペアレビュー → squash merge → Project 上で Issue が Done に移動 → マージ済みブランチ削除）
  • 「実装が止まったとき」の切り分け手順（① テスト失敗の原文を読む → ② spec.md の受け入れ基準と照合 → ③ plan.md / ADR の判断と矛盾していないか → ④ agy に状況を全文で渡す）を体に覚えさせる

SDD 実践プロジェクトの中間地点（Week10 → 11 → 12）

3週連続プロジェクトの 2 週目: 第10回 設計（spec / plan / ADR / Issue 化）→ 本日（第11回 実装: TDD + MCP + GitHub Flow）→ 第12回 検証と改善（テスト結果分析 + リファクタリング + セキュリティ観点）。今日は「動くもの」を増やす日。Issue を 1 枚 Done に移すたびに「今、何枚 Done か」が Project で見えるのが本日の楽しさ。全タスク完了は目指さなくてよい——「TDD サイクル 1 周 + GitHub Flow 1 周 + MCP 1 つ接続」を体験すれば本日は合格。

MCP（Model Context Protocol）とは何か(15分)

  • 本回で初登場の概念。1 行で言うと「agy に外部ツールを使わせるための統一プロトコル」
  • これまでの agy: テキスト生成 + ファイル編集 + シェルコマンド実行（一部）が中心 → MCP サーバーを繋ぐと、agy が GitHub API・データベース・Web fetch・社内 API 等を「自分の道具」として扱える
  • 本授業で扱う MCP の位置づけ:
    • 第8回ハーネスエンジニアリング入門で扱った「ハーネスの拡張点」の 1 つ。Hooks（実行前後で割り込む）に対して、MCP は「新しい道具を加える」拡張
    • 本日のゴールは「とりあえず 1 つ繋がる体験」。深い活用は第12回以降と進級制作の本実装で
  • 今日繋ぐ候補（講師事前検証済みの最小構成を 1 つ選んで配布、教室の Wi-Fi 状況・認証可否で当日選択）:
    • GitHub MCP server（Issue 一覧取得・PR 操作・file diff 取得が agy から直接叩ける。PAT 要）
    • Filesystem MCP server（プロジェクト外のファイルも安全に読み書き可能。設定が一番軽量）
    • Fetch MCP server（任意の URL を agy が取得して読み込み。第9回 Map で使った Open-Meteo を agy 内から直接叩ける）
今日の合言葉: 「analyze → implement → test → commit → PR の 1 周を、agy と一緒に体験する」。失敗してもよい。1 タスク Green になるまでの「つまずきの場所」を覚えて持って帰る回。

/speckit.implement × TDD サイクルで 1 枚目の Issue を Green に変える

feature ブランチを切る(5分) — GitHub Flow の起点

  • GitHub Project の Todo カラムから 1 枚目を選び、In progress に移動
  • その Issue 番号と短いタイトルから feature ブランチを作る: 
    # Issue #12 「[feat] 地図画面のルーティングを追加」の場合
git checkout main
git pull
git checkout -b feat/12-map-routing
  • ブランチ名規約: <type>/<issue-number>-<short-slug>（type は feat / fix / chore / docs 等。短い slug で他の人が一覧で分かるように）。GitHub Docs 公式: 「短く分かりやすいブランチ名を付けると、コラボレーターが一覧で進行中の作業を把握できる」

TDD サイクル Red(15分)

  • 第7回の復習: Red → Green → Refactor。最初に「失敗するテスト」を書いて、機能の輪郭を明確にする
  • agy に対する指示の出し方（spec.md と Issue の受け入れ条件を引用するのがコツ）: 
    Issue #12 (spec.md 受け入れ基準 1 に対応) のテストを先に書きます。
@specs/001-map-feature/spec.md の受け入れ基準 1 を満たすかを確認する
vitest のテストを src/__tests__/routing.test.js に追加してください。

期待する挙動:
- 「地図で見る」ボタンを押すと URL が /map に変わる
- /map では map ページのコンポーネントがレンダリングされる
- spec.md の非ゴール（ピンの色分け）はテスト対象に含めない

実装はまだ書かないでください。テストだけ追加して、npm test が
Red(失敗)になることを確認してください。
  • npm test を回し、書いたテストが 失敗することを確認（Red 達成）。「期待していた通りに失敗しているか」をテキストで読む（テスト名・期待値・実際値）
  • Red のテキストをそのまま貼って agy に共有してから Green に進む（agy にも「今は Red、これから Green に持っていく」と状況を伝える）

TDD サイクル Green(20分) — /speckit.implement を呼ぶ

  • /speckit.implement を呼ぶ。Spec Kit 公式: 「/speckit.implement はプランを実行する」。tasks.md と spec.md / plan.md を参照しながら、必要なファイルを編集してくれる
  • 本日の指示の出し方（Issue 1 枚分に絞る）: 
    /speckit.implement

tasks.md のうち、Issue #12 「地図画面のルーティングを追加」に
対応するタスクだけを実装してください。
他のタスクには触れないでください。

完了条件: src/__tests__/routing.test.js が npm test で Green。
  • agy が edit を提案してきたら、diff を必ず目で確認してから accept する。事故防止の鉄則は第8回ハーネス回と同じ
  • npm test を回し直して Green を確認（Red → Green 達成）
  • Green にならない場合の切り分け順:
    1. テスト失敗のメッセージ全文を読む（期待値・実際値・スタックトレース）
    2. spec.md の受け入れ基準と照合（テストが基準を正しく表現しているか）
    3. plan.md / ADR の判断と矛盾していないか（例: ADR で Leaflet 採用なのに Mapbox SDK を呼ぼうとしていないか）
    4. 上記 3 ステップを終えても解けないとき、状況を全文（テスト出力 + 直近の diff + 該当 spec 引用）を agy に渡して相談

TDD サイクル Refactor(10分)

  • Green が出たら、コードを読みやすくする段階。命名・関数分割・重複削除を行う
  • Refactor 中も npm test が Green であり続けることを確認する（リファクタの安全網がテスト）
  • commit する（意味の単位で 1〜3 commit にまとめると後の PR が読みやすい）。例: 
    git add src/__tests__/routing.test.js
git commit -m "test: add routing test for /map (refs #12)"
git add src/main.js src/pages/map.html
git commit -m "feat: add /map route and page component (refs #12)"
「テストが先」を体感する: 「実装してからテストを書く」のとは、agy への指示の出し方が変わる。テストが先にあれば「このテストを Green にして」の 1 行で目標が伝わる。テストがない状態で「機能を作って」と頼むと、agy は「何ができたら完成か」を解釈で埋めてしまい、想定外の挙動になりやすい。
休憩 10分

MCP サーバーを 1 つ接続 → 2 枚目以降を TDD で消化 → ハーネスの両輪を意識する

MCP サーバー接続(20分)

  • 講師事前検証済みの最小構成を配布（GitHub MCP / Filesystem MCP / Fetch MCP のいずれか 1 つ）。設定ファイルは ~/.gemini/config/mcp_config.json（Antigravity 公式 docs: 「Antigravity 2.0, IDE, and CLI share a central MCP configuration in the file ~/.gemini/config/mcp_config.json」）
  • 共通フォーマット: 
    {
  "mcpServers": {
    "<サーバー名>": {
      "command": "<実行コマンド>",
      "args": ["<引数1>", "<引数2>"],
      "env": {
        "<ENV_KEY>": "<値 or 環境変数参照>"
      }
    }
  }
}
  • 設定後、agy を再起動し /mcp を呼んで 接続済みサーバー一覧を確認（Antigravity 公式 docs: 「/mcp は manage MCP servers のスラッシュコマンド」）
  • 動作確認（配布された MCP の種類に合わせて 1 つ実行）:
    • GitHub MCP の場合: agy に「現在の Open Issue を MCP 経由で一覧してください」と頼む
    • Filesystem MCP の場合: agy に「~/Documents のファイル一覧を MCP 経由で取得してください」と頼む
    • Fetch MCP の場合: agy に「Open-Meteo の /v1/forecast?latitude=34.7&longitude=135.5 を MCP 経由で fetch して結果を見せてください」と頼む
  • つまずいたら1 タスク以上時間を使わない。MCP は今日のメイン目的ではなく「こういう拡張があるんだ」の体験が目的。失敗したら設定ファイルを git stash して 2 枚目のタスク実装に進む

2 枚目（と可能なら 3 枚目）の Issue を TDD で消化(25分)

  • 1 限後半と同じサイクル（Red → Green → Refactor → commit）を 2 枚目の Issue で繰り返す
  • 2 枚目以降は MCP を活用してもよい:
    • GitHub MCP がある場合: agy に「Issue #13 の本文を MCP 経由で取得してから tasks.md と突合して」と頼める（Issue 番号を渡すだけで agy が文脈を持ってきてくれる）
    • Fetch MCP がある場合: 第9回で使った Open-Meteo の応答を agy 内で取得してから実装方針を相談できる
  • 2 枚目のブランチは 1 枚目とは別に切る（1 PR = 1 機能を維持。後の Review が読みやすい）: 
    git checkout main          # main ではなく 1 枚目 PR を含む状態は避ける
git checkout -b feat/13-popup-display
  • 1 枚目の PR を出す前に 2 枚目を始めるのが一般的（PR レビュー待ちで自分の手が止まらないように）。main からブランチを切るが原則

ハーネスの両輪を意識する(5分)

  • Anthropic Engineering "Harness design" 由来の 2 軸を、今日の演習に当てはめて整理:
    • 事前制御（agy がやる前に止める）: spec.md の受け入れ基準・ADR の判断軸・Plan mode・.geminiignore・MCP のスコープ制限
    • 事後制御（agy がやった後にチェック）: npm test 緑確認・diff の目視・GitHub Actions の test.yml・PR レビュー
  • 今日 1 枚目で実感したのは「テスト Red を先に作ると agy の挙動が安定する」（=テストが事前制御の役を担っている）。Refactor 中も Green を維持できたのは「テストが事後制御の安全網になっている」
「全タスク終わらせる」が目的ではない: 今日のゴールは TDD 1 周 + MCP 1 接続 + GitHub Flow 1 周。3 枚目以降は家で進めて構わない。1 周をきれいに回す方が、5 枚を雑に進めるより 2 週間後の自分が助かる。
2限 後半 約30分

GitHub Flow を 1 周完走 — push → PR → レビュー → merge → Project 上で Done に

1 枚目を push して PR を作る(10分)

  • GitHub Flow 公式（GitHub Docs ja「GitHub フロー」）の 6 ステップ: ①分岐を作成 → ②変更を加える(commit & push) → ③pull request を作成 → ④レビューコメントに対処 → ⑤pull request をマージ → ⑥ブランチを削除。本日は 1 タスク分で 1 周完走することに絞る（複雑なレビューラリーは第12回以降と本実装で）
  • push: 
    git push -u origin feat/12-map-routing
  • PR 作成（gh CLI 推奨。Web UI でも同等）: 
    gh pr create \
  --title "feat: 地図画面のルーティングを追加 (#12)" \
  --body "$(cat <<'EOF'
## 概要
spec.md 受け入れ基準 1 に対応。/map ルート追加と map ページコンポーネントの新規作成。

## 関連
Closes #12

## Test plan
- [x] vitest の routing.test.js が Green
- [ ] ブラウザで /map に遷移できる(マージ後 Pages で確認)
EOF
)"
  • PR 本文に Closes #12 を入れると、マージ時に Issue が自動 close される（GitHub Docs 公式機能）

セルフレビュー or ペアレビュー(10分)

  • 近くの人とペアになり、互いの PR の Files Changed タブを 5 分ずつ見る
  • レビュー観点（最低限の 3 点）:
    1. spec.md の受け入れ基準と diff が対応しているか（受け入れ基準 1 のテストが追加されているか）
    2. diff に「やらないこと」（非ゴール）に手が伸びていないか（agy がスコープを超えて変更を加えていないか）
    3. テストが Green か（CI が緑バッジになっているか、ローカルで npm test が通るか）
  • 1 行コメントでよいので必ず何か残す。「LGTM」だけでも OK。レビューは「他人の目を入れる行為そのもの」が価値
  • 事前検証: gh pr create / gh pr view / gh pr review はいずれも Codespaces から動作する。失敗したら GitHub Web UI から手動で同等の操作が可能

merge → Project 上で Issue が Done に移動(10分)

  • Squash merge を選ぶ（main の履歴を 1 PR = 1 commit に保つ。第8回までで採用している運用）
  • マージ後の確認:
    • Issue #12 が自動 close されている（Closes #12 の効果）
    • GitHub Project の Issue 表示が Todo → In progress → Done に移動している（Project の自動化が有効な場合）
    • GitHub Actions の test.yml が main で Green を維持している
  • main 同期 + マージ済みブランチを削除（GitHub Flow ⑥ステップ目「ブランチを削除する」）。次のタスクに進む前に必ず: 
    git checkout main
git pull
# マージ済み feature ブランチをローカルから削除
git branch -d feat/12-map-routing
# リモート側も削除(squash merge 設定で自動削除されていない場合)
git push origin --delete feat/12-map-routing
# 必要なら 2 枚目のブランチを main から切り直し
    ※ GitHub リポジトリ設定で「Automatically delete head branches」を有効にしておくと、リモート側は merge と同時に自動削除される（推奨）
  • 1 周完走できれば本日の合格ライン到達。2 枚目以降は時間内であれば同じ流れで、間に合わなければ家での発展へ
GitHub Flow が遅いと感じるとき: 「ブランチを切る → PR → レビュー → マージ」は最初は手数が多く感じる。だが、「main に直接 push してすぐに動くものを変える」開発スタイルは、3 人以上のチーム・将来の自分・AI が編集する状況のすべてで事故が起きる。今日の 1 周は「事故が起きない手数」を体に通すための時間と捉える。
まとめ 約10分

必須
1 枚目の PR をマージ済みにする + マージ済みブランチを削除する

授業中に作った feat/<NN>-<slug> ブランチ の PR を、CI 緑・Closes #<NN> 記述付きで squash merge までやりきって push。マージ後に Issue が自動 close され、GitHub Project の表示が Done に移動していることを確認。最後に GitHub Flow ⑥ステップ目「ブランチを削除する」として、ローカル (git branch -d feat/<NN>-<slug>) とリモート (git push origin --delete feat/<NN>-<slug>) の両方から feature ブランチを削除する（リポジトリ設定で auto-delete を有効にしていればリモート側は自動）。

必須

必須
2 枚目以降のタスクを最低 1 枚 着手

家での発展として、2 枚目のタスクの feature ブランチを切り、Red のテストを書くところまでやりきる（Green まで行ければなお良し）。第12回の冒頭で 1 枚 In progress の状態から始められるように。
