GitHubでチーム開発をシミュレーションしよう

Week 5 木曜 1・2限

🎮 GitHubチーム開発シミュレーター（練習用）

ゲーム感覚で、チーム開発の流れ（clone → ブランチ → コミット → push → PR → マージ → コンフリクト解消）を体験できます。コマンドで打つモードとagyに自然言語でお願いするモードの両方があります。本物のGitHubには接続せず、入力内容はどこにも送信・保存されません。

→ シミュレーターを開く
テーマ
GitHubでチームで開発する流れ（ブランチ・PR・マージ・コンフリクト）を、シミュレーターで体験し、自分のリポジトリでもPRを1回作ってマージする
キーワード
ブランチ / コミット / push / プルリクエスト（PR） / マージ / コンフリクト / コマンドとagyの両方
必要な準備
第3〜4回の自分のリポジトリとゲーム。Codespaceは停止したままでOK——2限後半で「resume（再開）」して使う。

この回のゴール

  • チーム開発でブランチ・プルリクエスト（PR）・マージが必要な理由を、自分の言葉で説明できる
  • シミュレーターで、clone → ブランチ → コミット → push → PR → マージの流れを一通り体験する
  • コンフリクト（同じ行を2人が別々に変更したときの衝突）が起きる理由と、解消するときにどちらを残すか自分で決めることを体験する
  • 同じ操作をコマンドとagyへの自然言語のお願いの両方で行い、agyが裏で実行するコマンドを読んで、自分で打ったものと見比べる
  • 自分のリポジトリでも、agyに頼んで本物のPRを1回作り、自分でマージする
今日の優先順位: コマンドを暗記することよりも、「今、何が起きているか」を読めることを優先します。シミュレーターは何度でもやり直せるので、失敗しても大丈夫です。

授業の流れ

2コマ連続（90分 + 90分 = 計180分）。途中休憩あり。

1限 前半 約40分

なぜチーム開発にブランチとPRが必要なのかを知る

第2回のおさらい

  • 第2回で聞いた「ブランチ」「プルリクエスト」という言葉を思い出す——今日は初めて実際に操作する

2人が同じファイルを直すと、何が起きるか

  • 例: 2人が同じゲームのページの、同じ「見出し」の行を、同時に別々の内容に書き換えたらどうなるか——ブランチもPRも使わず、みんなが直接mainを編集し合うと、お互いの変更に気づかないまま進んでしまう
  • そこで、ブランチ（自分専用の作業ライン）で作業し、PR（「この変更をmainに取り込んでください」というお願い）でチームに見せて、レビューを受けてからマージ（mainに取り込む）する、というルールで進める

コンフリクトとは

  • 公式の説明: コンフリクトは、同じファイルの同じ行に、人によって違う変更が加えられたときなどに起きる（公式: Merge conflicts）
  • コンフリクトは失敗ではなく、どちらを残すか人間が決めるための合図。AIに任せきりにせず、自分で判断する場面になる

今日の進め方

  • シミュレーターには「コマンドで」と「agyにお願い」の2つのモードがある。同じミッションを両方で体験して比べる
  • シミュレーターは練習用で、本物のGitHubやagyには接続していない。入力した内容はどこにも送信・保存されない
1限 後半 約50分

シミュレーターで、ミッション1〜6（コマンドモード）を進める

シミュレーターを開く（チーム開発シミュレーター）

  • 「⌨ コマンドで」のタブのまま、ミッションを順に進める。困ったら「ヒントを見る」で次の一手が確認できる。help と打つと、使えるコマンドの一覧が出る
  • ミッション1: リポジトリをclone（git clone）
  • ミッション2: 作業用のブランチを作る（git switch -c add-title）
  • ミッション3: ファイルを編集してコミットする（git add . → git commit -m "…"）
  • ミッション4: GitHubにpushする（初回は git push -u origin ブランチ名。-u を付けずに git push だけを試すと、既定の設定では失敗する。何が起きるか試してみる）
  • ミッション5: PRを作る（疑似GitHub画面の「Compare & pull request」ボタン、または gh pr create）
  • ミッション6: ミサキのレビューを受けて、「Merge pull request」でマージする

途中で気づいたことを共有する

  • 「ブランチの図」と「ファイルの中身」を見比べ、コマンドを実行するたびに何が変わったかを確認する
  • わざと間違えたコマンドを打って、どんなメッセージが返ってくるか試してもよい
休憩 10分
2限 前半 約50分

コンフリクトを解消し、次にagyに頼んで同じことをやり直す

ミッション7・8: コンフリクトに挑戦する（コマンドモード）

  • 「▶ 2本目の作業を始める」で、ミサキと同じ行を別々に変更してしまった状況を作る。PRを作ると、コンフリクトの表示が出る
  • git pull origin main で最新のmainを取り込み（実際のgitでは、設定によって「どう取り込むか指定してください」と止まることがある。その場合は git pull --no-rebase origin main を使う）、ファイルに現れた印（<<<<<<< / ======= / >>>>>>>）を読む。上が自分、下がミサキの変更
  • 「自分の変更」「ミサキの変更」「両方」のどれを残すか、自分で決める（正解は1つではない。理由を隣の人と話してみる）
  • git add . → git commit -m "…" → git push で解消し、PRをマージする（公式: Resolving a merge conflict using the command line）

agyモードで、最初からやり直す

  • 「最初からやり直す」を押し、今度は「🤖 agyにお願い」のタブで同じミッションを進める
  • 例: このリポジトリをcloneして → ブランチを作って、タイトルを変更して、コミットして → pushして → PRを作って
  • シミュレーターのagyは実行するコマンドを見せて、確認してから実行する（本物のagyは、既定では実行前に承認を求められることが多いが、設定によっては自動で実行される。承認の出方はシミュレーターと異なる。公式: Permissions）。agyが実行するコマンドを、さっき自分で打ったものと見比べる——多くの場合、gitやghのコマンドが使われる
  • コンフリクトの解消では、指示が曖昧だとagyから聞き返されることがある。どれを残すかという中身の判断は自分で伝える必要があることを確かめる
比べてみよう: コマンドは自分が何を実行したかが確実に分かります。agyへのお願いは楽で速いですが、裏で何が実行されたかを読めることが、AIに任せるときの安心につながります。どちらが向いている場面か、隣の人と話してみましょう。
2限 後半 約30分

自分のリポジトリで、本物のPRを1回作ってマージする

Codespaceを再開して、agyを起動する

  • 第4回と同じ手順で、自分のリポジトリのCodespaceを再開（resume）し、新しいターミナルで agy を起動する（ログインを求められたら第3回と同じ手順でやり直す）
自分のWindows PCで開発するとき: 今日のagyはCodespaces上で使います。Codespacesの中は、手元のPCがWindowsでもLinuxなので、第3回のコマンドのままで動きます。ただ、自分のWindows PCにagyを入れて使う場合は、インストールのコマンドが違います。
  • Windows（PowerShell）: irm https://antigravity.google/cli/install.ps1 | iex
  • Windows（コマンドプロンプト）: curl -fsSL https://antigravity.google/cli/install.cmd -o install.cmd && install.cmd && del install.cmd
  • Mac・Linuxは、第3回の curl -fsSL https://antigravity.google/cli/install.sh | bash
コマンドが違う理由は第3回の補足に書いてあります。公式はAntigravity CLI — Installation & authを見てください。

agyに頼んで、ブランチを作って変更する

  • 例: add-messageという名前のブランチを作って、ゲームのどこかに一言メッセージを追加して、コミットしてpushしてください
  • agyが実行するコマンドを、さっきのシミュレーターと見比べる

GitHubの画面でPRを作って、マージする

  • GitHub上の自分のリポジトリを開く。pushした直後は「Compare & pull request」のボタンが出る（しばらくすると消えるので、その場合は「Pull requests」タブから作れる）（公式: Creating a pull request）
  • タイトルを確認して「Create pull request」を押し、続けて「Merge pull request」→「Confirm merge」の順に押してmainに取り込む（公式: Merging a pull request）
  • 1人のリポジトリなので、コンフリクトは起きない。自分ひとりでもPRを使うと、変更の履歴が残ることを確認する
Codespaceのブランチについて: マージしたあとは、Codespace側のブランチがmainと食い違うことがあります。次回以降の作業に影響しそうなときは、講師に声をかけてください。
まとめ 約10分

推奨
