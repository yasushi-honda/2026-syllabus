agyと一緒につくる②

Week 5 木曜 1・2限
テーマ
第4回の続き。agyと一緒にゲームを改善・仕上げして、GitHub Pagesでインターネットに公開する
キーワード
改善・仕上げ / GitHub Pages / 公開URL / 更新の反映 / 振り返りメモ
必要な準備
第4回までのリポジトリとゲーム（Publicのまま）。Codespaceは停止したままでOK——今日も「resume（再開）」で続きから始める。

この回のゴール

  • 第4回の続きとして、ゲームを改善・仕上げする（機能追加・見た目・不具合の修正）
  • agyに、公開に必要なファイル（index.html）が整っているかを確認・整えてもらう
  • GitHub Pagesを有効にして、自分のゲームを公開URLで誰でも開ける状態にする
  • 公開後に修正して、プッシュ→数分待つ→公開URLに反映される流れを体験する
  • 取り組みの過程で気づいたことを振り返りメモに残す
今日の優先順位: 完成度を上げきることよりも、「自分が作ったものが自分の公開URLで開ける」ところまで到達することを優先します。改善は公開後も続けられます。

授業の流れ

2コマ連続（90分 + 90分 = 計180分）。途中休憩あり。

1限 前半 約40分

Codespaceを再開し、今日の改善ポイントを決める

Codespaceを再開して、ゲームを動かす

  • 第4回と同じ手順で進める——自分のリポジトリの「Code」→「Codespaces」タブから、停止中のCodespaceをクリックして再開する（「Create codespace on main」で新しく作り直さない）
  • ターミナルで python3 -m http.server 8000 を実行し、「ポート」タブの8000番の「エディターでプレビュー」でSimple Browserにゲームを表示する
  • http.serverを動かしているターミナルはそのままにして、新しいターミナルを開き agy を起動する（ログインを求められたら第3回と同じ手順でやり直す）

今日の改善ポイントを決める

  • ゲームを実際に遊んでみて、「もっとこうしたい」を1〜3個書き出す。次の3つの視点で探すと見つけやすい
    • 見た目: 色・文字の大きさ・レイアウト・スマホの画面でも見やすいか
    • 操作: 遊び方が初めての人にも伝わるか、リスタートやポーズがあるか
    • 不具合: 思った通りに動かない箇所・エラーが出る箇所はないか
  • 書き出した中から、効果が大きそうなものから順に並べる。公開までの時間を確保するため、今日全部やろうとしなくてよい
1限 後半 約50分

agyと対話しながら、ゲームを改善する

改善を1つずつ指示する

  • 優先順位の高いものから、agyに自然言語で伝える。第4回で学んだとおり、何を・どこに・どう動いてほしいかを具体的に書くと伝わりやすい
  • 1回の指示に詰め込みすぎず、1つ直す→ブラウザで確認→次を伝えるの順で進める（Simple Browserは更新ボタンで再読み込みする）
  • 思った通りでなければ、違う点をそのままagyに伝え直す。エラーの意味が分からなければ これはどういう意味ですか？ と聞いてよい

公開に向けた確認をagyに頼む

  • GitHub Pagesは、公開する範囲の一番上にある入口のファイル（index.html）を探して表示する（公式: Creating a GitHub Pages site）
  • ゲームのファイル名が tetris.html のように index.html ではない場合は、agyに次のように頼む（例）: このゲームを公開URLのトップページで開けるように、index.htmlという名前にしてください
  • あわせて、公開してはいけない情報がファイルに入っていないか確認する（次の注意を参照）
公開するということ: GitHub Pagesで公開したサイトは、インターネット上の誰でも見られます（公式: Configuring a publishing source for your GitHub Pages site）。リポジトリのファイルもPublicのため誰でも読めます。本名・住所・電話番号などの個人情報や、パスワード・APIキーなどの秘密の文字列は、コードにもメッセージにも書かない・書かせないようにしましょう。
休憩 10分
2限 前半 約50分

変更をプッシュして、GitHub Pagesで公開する

今日の変更をコミット・プッシュする

  • 第4回と同じく、agyに ここまでの変更をコミットして、GitHubにプッシュしてください と頼む
  • GitHub上で自分のリポジトリを開き、ファイルが更新されていることを確認する

GitHub Pagesを有効にする（公式: Configuring a publishing source for your GitHub Pages site）

  • GitHub上の自分のリポジトリで「Settings」を開く
  • 左のメニューの「Pages」を選ぶ
  • 「Build and deployment」の「Source」で「Deploy from a branch」を選ぶ
  • ブランチはmain、フォルダは/ (root)を選んで「Save」を押す

公開されるのを待つ

  • 公開までには最大10分ほどかかることがある（公式: Creating a GitHub Pages site）。「Pages」の画面にサイトのURLが表示されたら公開完了
  • URLは https://（自分のGitHubユーザー名）.github.io/（リポジトリ名）/ の形になる
  • 待っている間は、Codespaceに戻って次の改善を進めてよい
公開URLで404（ページが見つかりません）と出たら: 公開直後は反映に時間がかかることがあります。数分待って再読み込みしても変わらない場合は、①リポジトリの一番上にindex.htmlがあるか、②Pagesの設定でブランチがmain・フォルダが/ (root)になっているか、を確認し、それでも直らなければ講師に声をかけてください。
2限 後半 約30分

公開URLで確認し、修正が反映される流れを体験する

公開URLで動作を確認する

  • 公開されたURLを、ブラウザの新しいタブで開き、ゲームが動くことを確認する
  • 可能なら、スマホやとなりの人のPCでも開いてもらい、自分以外の環境でも開けることを確認する

修正して、公開に反映されるまでを体験する

  • 気になった点を1つだけagyに直してもらう→確認→コミット・プッシュ→数分待って公開URLを再読み込みする
  • 「プッシュしただけでは公開URLにすぐ反映されず、少し待つ必要がある」ことを実際に確かめる
公開URLを控える: 自分の公開URLは、次回以降の発表や共有で使います。忘れないようにメモしておきましょう。
まとめ 約10分

次回予告＆振り返りメモ

  • 次回（第6回）：Google AI Studio Build modeに触れてみよう①——第3〜5回でagyと育てたこのリポジトリを、ブラウザだけで使うGoogle AI Studio Build modeに「Import from GitHub」で読み込み直す。リポジトリ名を忘れずに控えておく
  • 今日の振り返りメモを書いて退出する——①agyに指示を出す中で気づいたこと（うまく伝わった指示・伝わらなかった指示）、②公開してみて感じたこと、を一言ずつ
  • 使い終わったCodespaceは、Codespacesの一覧から停止しておく

課題・次回までにやること

必須
自分の公開URLとリポジトリ名を控えておく

公開URLをブラウザで開いてゲームが動くことを確認し、リポジトリ名とあわせてメモしておく。公開が間に合わなかった場合は、次回授業の冒頭で完了させる。

推奨
友達や家族に公開URLを見せてみる

自分以外の人に遊んでもらい、分かりにくかった点を聞いておくと、第6回以降の改善のヒントになります。
