1限 前半 約40分

Build modeとは何か——agyとの違いを対比表で知る

第5回のつづき——GitHubが「ハブ」になる

  • 第3〜5回で、自分のゲームはGitHubのリポジトリに入っている。リポジトリは、Codespaceが停止しても残る「自分の作品の置き場所」
  • 置き場所がGitHubにあるので、agy以外の道具からも、同じ作品を読み込める。今日はその道具としてGoogle AI Studioを使う

第1回の軸にあてはめる——チャット型AI と AIエージェント

  • 第1回で、聞けば答えてくれるチャット型AIと、指示を受けて自分でタスクを進めるAIエージェントを区別した。今日の道具を、この軸に置いてみる
  • Google AI Studioには、会話しながら試すChatの画面（チャット型。公式: Google AI Studio quickstart）と、今日使うBuild modeの画面（公式: Build apps in Google AI Studio）がある。Build modeは、ファイルを作ってアプリとして動かすところまで進めるエージェント側の画面

Build modeとは

  • Google AI Studioの中の機能で、自然言語で指示を書くと、AIがコードを書き、アプリとして動く様子が右側のプレビューに出る（公式: Build apps in Google AI Studio）
  • 中身はagyと同じ系統のエージェント。公式原文: "The Antigravity Agent is the main AI functionality within Google Antigravity and now the core components of the agent harness is powering the Build mode experience in Google AI Studio."——エージェントを動かす土台（エージェントハーネス）の中核部品が、Build modeの裏で動いている。agyも同じAntigravityの土台の上で動く（公式: Antigravity CLI overviewの「Both environments run on the same agent core」は、AntigravityアプリとCLIの関係の説明で、AI Studioとの直接の記述ではない）。公式に書かれているのは「中核部品」までで、agyの機能がすべて同じ形で入っているとは書かれていない（次の対比表を参照）
  • つくられるもの: Webアプリが既定で、画面側（既定はReact）とサーバー側（Node.js）の両方を持つアプリになる。ほかにKotlinのAndroidアプリも選べる。生成されたコードは、右側のCodeタブで見られる
  • 続け方: チャット欄で指示を追加する／Codeタブで直接書き換える／annotation mode（アプリの画面の一部を選んで、変えたいことを言葉で伝える）
  • どちらが優れているかを決める回ではない。同じ作品を両方で触って、違いを自分で感じるのが今日のねらい

agyとBuild modeの対比表（公式ドキュメントで2026-10-15に確認）

観点 agy（Antigravity CLI） Build mode（AI Studio）
画面・場所 黒い画面（ターミナル）。この授業ではCodespaceの中 ブラウザ（aistudio.google.com）。左で指示、右でプレビュー
指示の出し方 自然言語に加えて、/で始まるスラッシュコマンド（/plan・/agentsなど） 入力欄に自然言語。音声入力、AI Chips、画面の一部を選ぶ annotation mode
動かして確かめる この授業では自分でサーバーを起動し、ブラウザで開いて確かめた（第4回） 右側のライブプレビューに、生成のたびに出る
変更の承認 既定では、ファイルを書き換える前に差分を見せて聞く（y / n）。accept-editsで自動承認にもできる 公式の説明ページには書かれていない
Planモード ある。Shift+Tabで切り替え。読み取りだけで調べて実行計画を示し、承認を待つ 公式の説明ページには書かれていないが、画面にはある。入力欄の近くのモード切り替えに Default・Plan・Max を選ぶスライダーがあり、Defaultは「Make changes right away」（すぐ変更を加える）。Planで何が変わるかは、2限で確かめる
Skills ある。SKILL.mdを入れたフォルダ（.agents/skills）。エージェントが一覧を見て、関係がありそうなときだけ中身を読む 公式の説明ページには書かれていない。画面にあるか、2限で探す
考える深さ（effort） 調整できる。/effortでlow・medium・highから選ぶ（モデルによってはxhigh・maxも）。軽い修正は速く、難しい問題は深く考えさせる使い分けができる 公式の説明ページには書かれていない。調整の項目があるか、2限で探す。モード切り替えの Max が何を変えるのかは、まだ確認できていない
そのほかの拡張 Rules（守らせたい決まり）・並行して動くサブエージェント・MCP・プラグイン どれも説明ページには書かれていない。代わりに、FirestoreやGoogle Workspace連携を自動で設定する
作れるもの 手元のプロジェクトのファイル全般。許可すればコマンドも実行する Webアプリ（画面＋Node.jsのサーバー）または、Kotlinで作るAndroidアプリ
GitHubとの付き合い方 gitのコマンド、または自然言語でお願いする（第2〜5回） SettingsのGitHubタブで双方向に同期。pushにはAIが書いたコミットメッセージが付き、競合は Resolve conflicts の画面で選ぶ。初回は、新しいリポジトリか、既存リポジトリへの Force push を選ぶ（教員の画面で確認。実際の動きは、元の履歴にコミットを足すだけだった）。連携後は、Pullが先、Pushが後（教員の画面で確認）
公開・持ち出し GitHubへpushして、GitHub Pagesなどで公開（次回） 共有URL、Cloud Runへデプロイ、ZIPで書き出し
表の読み方: 「公式の説明ページには書かれていない」は、「ない」とは違います。ページに載っていないだけで、画面にはある、あるいは近いうちに増える可能性があります（AI Studioは機能の追加が速い）。実際に、Planモードは、説明ページに載っていないのに画面には出ていました（2026-10-15、教員の画面で確認。アカウントや時期で表示が違う可能性があります）。この欄は2限で、実際の画面を見て確かめる課題にします。出典: Choose an execution mode（Antigravity公式） / Agent skills（Antigravity公式） / Effort command (/effort)（Antigravity公式） / Rules（Antigravity公式） / Custom subagents（Antigravity公式） / Build apps in Google AI Studio（Google公式）

使うアカウントについて

  • Googleアカウントでログインする。学校用・個人用どちらでもよい（第3回のagyと同じ。本科目ではアカウントの種類は問わない）
  • 公式には、Workspace for Educationのアカウントでは18歳未満は使えないと書かれている（Access Google AI Studio with your Workspace account）。本校の学生は全員18歳以上なので、この年齢の制限には当たらない。ただし、組織の管理者が設定でオフにしていると学校用では開けないことがある。そのときは個人用のGoogleアカウントで進める
  • 今日は、支払いや請求の設定は一切しない。画面で有料や請求に関する案内が出たら、進まずに講師に声をかける
1限 後半 約50分

自分のリポジトリを取り込み、プレビューで動かす

取り込む

  • 公式の説明: Build modeで、プロンプト入力欄のAdd files（＋のアイコン）メニューからImport from GitHubを選ぶと、既存のコードを取り込める。プロンプトを実行すると、必要なコードとファイルが生成され、アプリのライブプレビューが表示される（Build apps in Google AI Studio）
  • 取り込むのは、第3回で作った自分のリポジトリ（第5回で名前を控えたもの）。リポジトリはPublicのままにしておく（第3回で案内したとおり）
  • 取り込んだあと、プロンプト欄に最初の指示を書いて送信する。例: 取り込んだコードのゲームの遊び方を、初心者向けに3行で説明してください。コードは変えないでください

まず「何も変えずに」確かめる

  • 右側のプレビューで、元のゲームが動くかを確かめる。遊んでみて、第4〜5回に作った機能が残っているかを見る
  • 取り込んだコードは、書き直されたり、ファイルの構成が変わったりして、元のゲームと見た目や構成が変わることがある。教員の画面では、取り込み直後に警告のバナーが出た: "Your imported app is ready and contains a major rewrite. Gemini rewrote significant parts of the codebase to ensure compatibility with Google AI Studio."（取り込んだアプリは準備できたが、大きな書き直しを含む。AI Studioで動くように、Geminiがコードの重要な部分を書き直した）。公式の説明ページには、取り込んだコードの扱いは書かれていない（Build modeは、既定で画面とサーバーの両方を持つアプリを作る仕組みと説明されている）。変わっていたら、どこが違うかをメモする——失敗ではなく、2限の観察の材料になる
  • 書き直されるのは、AI Studio側のコピーと考えられる。教員が取り込んだだけの時点では、元のGitHubのリポジトリにコミットは増えていなかった（教員のリポジトリの履歴で確認）。GitHubが変わるのは、自分で送る操作をしたときのはず。ただし、自動で送られないと言い切れる確認ではないので、送る操作は、第7回に、備えをしてから、みんなで一緒に行う。今日は、GitHubタブも、バナーの「Sync to GitHub」も押さない
  • 動かない、読み込みが進まない、リポジトリが一覧に出ないときは、講師に声をかける。エラーが出たら、その全文をプロンプト欄に貼って「原因と直し方を教えて」と頼んでもよい
今日は押さない場所: AI Studioの設定（歯車）にあるGitHubタブと、取り込み直後のバナーの「Sync to GitHub」ボタンは、同じ「GitHubへ送る」画面につながる。選択肢には「Force push」があり、説明は「main branch will be replaced with this app's code」（教員の画面で確認）。教員が試した範囲では、元の履歴にコミットが1つ足されるだけだったが、条件によって動きが違うかもしれない。GitHubへ送る操作は、第7回に、先にbackupを作ってから、みんなで一緒に行う。今日は、押さない。

自然言語で続きを作る——agyのときとの違いを観察する

やること（約35分）

  • 取り込んだゲームに、自然言語で改善を1つずつ頼む。例: スコアの表示を大きくする、ゲームオーバーの画面を作る、難しさを選べるようにする、色や見た目を変える
  • 第4回に学んだとおり、あいまいな指示より、具体的な指示のほうが思ったものに近づく。思い通りにならないときは、「何が違うか」を言葉にして追加で指示する
  • 1つ指示するたびに、プレビューで遊んで確かめる。確かめてから、次の指示に進む
  • 余裕があれば、annotation mode（アプリの画面の一部を選んで、変えたいことを言葉で伝える）も試す。言葉だけでは伝えにくい「ここを」を、画面を指して伝えられる（公式: "Annotation mode lets you highlight any part of your app's UI and describe the change you want."）

agyのときとの違いを観察する（メモを取りながら、約15分）

  • ①指示を出してから、結果が見えるまでの流れはどう違うか（プレビューの有無）
  • ②どのファイルが、どう変わったかは、どこで分かるか（Codeタブや、ファイル一覧を探してみる）
  • ③思い通りにならなかったとき、やり直しや直し方はどう違うか（設定の画面にVersionsというタブがある。何が見られるか、開いて確かめる）
  • ④取り込み直後に気づいた「元との違い」は、使っているうちに影響が出たか
  • ⑤対比表の「書かれていない」欄を、実際の画面で確かめる（約5分）。教員の画面では、入力欄の近くにモード切り替えのスライダー（Default／Plan／Max）がある。自分の画面にもあるか見つけ、Planに切り替えて、まだ試していない新しい改善を1つ頼み、Defaultのときの動き（指示するとすぐ変更が入った）とどう違うかを観察する。同じ指示のやり直しは、すでに変更が入った状態になるので比べられない。見るのは、先に計画が出るか、承認を求められるか、コードがすぐ変わるか、など（agyのplanモードは、コードを書く前に計画だけ見せる使い方）。Maxは何と説明されているかも読んで、メモする。あわせて、Skills・Rules（決まりごとを前もって渡す）や考える深さ（effort）の調整にあたる設定が画面にあるかも探す。見つけたら、画面の名前をメモして講師に教える。見つからなくても、それが今日の結果。なお、AI Studioの別の画面（Agents in AI Studio）にはSkills（SKILL.md）の説明があるが、Build modeとは別の機能なので、そちらは数えない。

Gemini APIの自動設定を確かめ、振り返りメモを書く

Gemini APIを使う機能（任意、約15分）

  • 公式の説明: Gemini APIを使う新しいアプリを作ると、AI StudioがGemini APIキーを、アプリのサーバー側の環境のシークレットとして自動で設定する。キーは「Secrets」パネルで確認・管理できる（Build apps in Google AI Studioの「API Key management」）。つまり、自分でAPIキーを書かなくてよい
  • 試す人は、例えばゲームオーバーのときに、Geminiがひとことコメントを出す機能を足してくださいと頼む。出てきた画面の案内を読んで進める。公式の説明は「Gemini APIを使う新しいアプリを作ると」という書き方なので、取り込んだアプリでも同じように設定されるかは公式に書かれていない。SettingsのSecretsパネルで、実際にキーが設定されているかを確かめる
  • APIキーは、コード・チャット・スクリーンショットのどこにも貼らない。公式には、キーはサーバー側で扱われると書かれている（ブラウザ側のコードに書いてしまうと、ページを開いた人に見えてしまう）
  • 公開について（次回）: GitHub Pagesは、HTML・CSS・JavaScriptのファイルを置いて公開する静的サイト向けの仕組み（公式: What is GitHub Pages?）。サーバー側で動く処理に頼る機能は、そのままでは動かない可能性がある。また、Geminiのキーをブラウザ側のJavaScriptに直接書いて公開すると、誰にでも見えてしまう。公開できるかは、次回に確かめる
