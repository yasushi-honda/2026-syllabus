この回のゴール

  • 公開 URL を QR コードに変換し、スマホで読み取って実機確認できる
  • <meta name="viewport"> が「スマホで縮小表示しない」ための宣言であることを自分の言葉で説明できる
  • メディアクエリ（@media (max-width: ...)）の基本構文を手で書ける
  • Chrome DevTools のレスポンシブモードで複数の画面幅を試せる
  • AI が生成した「バグ入りスマホ対応 CSS」を読み解き、採用するか・修正するか・捨てるかを自分で判断できる

1限 前半 約40分

公開 URL を QR コード化 → スマホで実機確認する

前回の振り返り(10分)

  • 第4回で取得した自分の公開 URL(https://<ユーザー名>.github.io/<リポジトリ名>/)を取り出す
  • 第4回の課題で家のスマホで撮ったスクリーンショットを手元に置く——今日の素材になる
  • Codespaces を起動し、python3 -m http.server 8000 → Simple Browser で表示確認(第1回と同じ手順)

QR コードに変換する(15分)

  • QR コード生成サービスを開く——おすすめは qr.quel.jp(日本語) または QRCode Monkey(英語)。どちらも無料、登録不要
  • 入力欄に公開 URL を貼り付け→ 生成ボタン → PNG をダウンロード
  • 生成された QR を Codespaces の画面に表示するか、PC の隣に並べてスマホで読み取る
  • iPhone は標準カメラアプリ、Android は標準カメラ or Google レンズで QR を認識

スマホで実機確認する(15分)

  • QR から開いた公開 URL を、縦持ち・横持ちの両方で確認
  • 第4回の家で撮ったスクショと見比べて、気になる点を口に出す:
    • 「文字が小さい」「画像がはみ出る」「余白が詰まりすぎ」「ボタンがタップしづらい」など
  • クラスメイトに自分の QR を見せて公開 URL を覗いてもらうのもよい(今日は public リポジトリ前提なので問題なし)
QR コードに有効期限はない: 公開 URL が変わらない限り、生成した QR は何度でも使えます。スマホの「写真」アプリに保存しておくと、後の回でも実機確認に使えて便利。
1限 後半 約50分

「なぜ崩れるか」を viewport メタタグとメディアクエリで理解する

なぜ PC とスマホで違って見えるか(15分)

  • PC のブラウザは画面幅が広い(1280px / 1920px など)、スマホは狭い(360px / 414px など)
  • スマホはデフォルトでは 「擬似的に約 980px 幅」 として PC 向けのページを縮小表示しようとする(MDN「レスポンシブウェブデザイン」の説明)——これが「文字が小さい」の正体
  • これを止めて「端末の実際の幅でレイアウトしてね」と伝えるのが viewport メタタグ

viewport メタタグを書く(10分)

  • 第1回からの雛形にはすでに入っているはず——<head> 内を確認: 
    <meta name="viewport" content="width=device-width, initial-scale=1.0">
  • width=device-width: ビューポート幅を端末の実際の幅に合わせる
  • initial-scale=1.0: 初期倍率を100%にする(縮小表示しない)
  • もし無かったら追加してリロード——スマホ実機での「文字の小ささ」が変わるはず(変わらない人はクラスメイトとペアで比較)

メディアクエリの考え方(15分)

  • viewport を入れただけでは「縮小されない」だけ。レイアウト自体をスマホ向けに変えるには、画面幅に応じた CSS の出し分けが必要
  • その出し分けの仕組みが メディアクエリ(@media)
  • 基本構文: 
    @media (max-width: 600px) {
  /* 画面幅が 600px 以下のときだけ
     ここに書いた CSS が適用される */
  body { font-size: 14px; }
  img  { width: 100%; }
}
  • ブレイクポイント: 「ここで切り替える」と決める画面幅のこと。よく使う値は 600px / 768px / 1024px(MDN の作例にも 600px / 1200px がよく登場する)

DevTools のレスポンシブモードを開く(10分)

  • Chrome の Simple Browser や別タブで公開 URL を開き、F12 または 右クリック → 検証 で DevTools を開く
  • 左上のスマホ/タブレットアイコン(Toggle device toolbar)をクリック → レスポンシブモードに切り替わる
  • 画面上部の幅(例: 375 × 667)を変えて、PC でスマホ表示を再現できる——QR で実機を見られない時はこれで代用
  • 「Responsive」と書かれた左上のプルダウンで、iPhone / Pixel / iPad など実機相当の幅プリセットも選べる
休憩 10分
2限 前半 約50分

メディアクエリを手で書いてスマホ表示を整える

気になる点を1つに絞る(5分)

  • 1限前半のスマホ実機確認で出た「気になる点」のうち、1つだけを選ぶ
  • 典型例:
    • 「見出し(h1)が大きすぎてスマホで2行に折り返してしまう」
    • 「画像が画面からはみ出している」
    • 「左右の余白(padding)が広すぎて中身が窮屈」
  • 全部直そうとしない——1問解いてから次へ

手でメディアクエリを書く(25分)

  • style.css の末尾に追記する。元の CSS は触らない(切り戻せるように)
  • 例: 見出しがスマホで大きすぎる場合 
    /* スマホ向け(600px 以下) */
@media (max-width: 600px) {
  h1 { font-size: 1.5rem; }
  p  { font-size: 0.95rem; }
}
  • 例: 画像が画面からはみ出す場合 
    img {
  max-width: 100%;
  height: auto;
}

    ※これはメディアクエリ無しでも効く基本ルール。スマホ専用ではなく常に有効にする

  • 例: 左右の余白を狭くする場合 
    @media (max-width: 600px) {
  body { padding: 0.5rem; }
}
  • 1つ書くたびに DevTools のレスポンシブモードで確認 → スマホ実機(QR)で確認、を繰り返す

commit & push(10分)

  • 「ソース管理」タブで変更内容を確認 → コミットメッセージ例: スマホ向けメディアクエリを追加
  • 「Commit」→「Sync Changes」で push
  • GitHub Pages の反映を待つ(最大10分、通常1〜3分)→ スマホで QR を読み直して確認

うまくいかない時のチェックリスト(10分)

  • ① メディアクエリ内の CSS が効かない → 中括弧 { } の対応をチェック。@media の { と中の各セレクタの { で2重のネストになっていることを確認
  • ② 画面幅を変えても何も変わらない → viewport メタタグが <head> に入っているか確認
  • ③ ブラウザの表示が古いまま → Cmd(Ctrl) + Shift + R で強制再読み込み
  • ④ スマホでだけ崩れる → DevTools のレスポンシブモードで該当幅を再現してから直す方が早い
2限 後半 約30分

🔧バグ修正ワーク①: AI が書いた「バグ入りスマホ対応 CSS」を直す

このワークの意図(5分)

  • AI(GitHub Copilot や Gemini など)はもっともらしい CSS を一瞬で書く——でも全部が正しいとは限らない
  • 「AI に書いてもらって動いた」で止まると、自分のスキルにならない
  • 今日のワークは「わざとバグを混ぜた CSS を AI に書かせて、自分で読み解いて直す」

AI にバグ入り CSS を頼む(10分)

  • Codespaces 内蔵の Copilot Chat、または Gemini を開く
  • プロンプト例(コピペ可): 
    HTMLのプロフィールページをスマホ対応するCSSを書いてください。
ただし、わざと「3箇所」だけ間違いを混ぜてください。
たとえば、プロパティ名のスペルミス、単位の付け忘れ、
メディアクエリの構文ミスなどです。
「どこに間違いを混ぜたか」は最後まで教えないでください。
  • 生成されたコードをそのまま style.css の末尾に貼り付ける(本来の CSS が壊れないように分離)
  • ブラウザでリロード → 期待通り動いていない箇所が出るはず

3つのバグを探して直す(15分)

  • 1行ずつ声に出して読む:「セレクタはこれ、プロパティは font-size、値は 16……あれ、単位の px が無い」のように
  • DevTools の「Elements」タブで該当要素を選択 → 右側の「Styles」で適用されていない CSS(取り消し線)を探す——これは強力なヒント
  • 見つけたバグを自分の言葉でメモ: 「① padd は padding のスペルミス / ② max-width 600px は : が抜けている / ③ @media screen の後の and が抜けている」など
  • 直し終わったら AI に「3箇所のバグを答え合わせしてください」と聞いて、自分の発見と照合する
  • すべて発見できなかった人は、自分が見落とした理由を1行メモ——次回以降の自分への申し送り
「AI が出したコードを採用するかどうか」の判断材料: ① 自分で読めるか(読めないコードは採用すると後でメンテできない)、② 動作確認したか(見た目で動いていても、別の場所が壊れていないか)、③ 第三者(クラスメイトや講師)に説明できるか。「動いた」だけで採用しない癖をつける。
