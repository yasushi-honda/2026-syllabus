ミニ完成①プロフィールサイト公開

Week 4 火曜 1・2限
テーマ
第3回までに書いた index.html + style.css を GitHub Pages 経由でインターネット上に公開し、自分の公開URLを取得する
キーワード
GitHub Pages / Settings → Pages / Deploy from a branch / 公開URL / プロジェクトサイト / 個人情報を載せない判断 / commit & push
必要な準備
第3回までに commit & push 済みの index.html + style.css を含む自分のリポジトリ・Codespaces が起動できる状態

この回のゴール

  • GitHub Pages が「リポジトリ上の HTML/CSS をそのまま Web に公開する仕組み」であることを自分の言葉で説明できる
  • Settings → Pages の操作だけで自分のサイトが公開URLを持つことを体験する
  • 公開URLにブラウザ・スマホからアクセスし、第三者の目で自分の作品を確認できる
  • プロフィールに何を載せるか・何を載せないかを自分で判断できる（個人情報の扱い）
  • 反映までの待ち時間（最大10分）と、変更後の再デプロイの仕組みを理解する

授業の流れ

2コマ連続(90分 + 90分 = 計180分)。途中休憩あり。

1限 前半 約40分

「公開する」とは何かを理解し、公開前の最終チェックを行う

前回の振り返り(10分)

  • 第3回で書いた index.html + style.css を Codespaces で開き直す
  • python3 -m http.server 8000 → Simple Browser で表示確認(第1回と同じ手順)
  • 第3回で commit & push したかを確認する。まだなら、今この場で実行する

「公開する」とは何か(15分)

  • これまでの Simple Browser は Codespaces 上の自分にしか見えないプレビュー
  • GitHub Pages を有効化すると、リポジトリ内の HTML/CSS が https://<ユーザー名>.github.io/<リポジトリ名>/ という URL で誰でもアクセスできる状態になる
  • 公開後は、URL を知っている人は誰でも見られる——プライベートではないことを最初に確認
  • これが「プロジェクトサイト」の公開方式。username.github.io という名前のリポジトリを別途作る「ユーザーサイト」もあるが、今日はリポジトリ名を変える必要がないプロジェクトサイト方式でいく

公開前の3つの最終チェック(15分)

  • ① ファイル名: トップページは必ず index.html。他の名前にすると公開URLで「Not Found」になる
  • ② 個人情報チェック: 本名・住所・電話番号・通学先など、公開して困る情報が入っていないかを見直す(後述の「載せる/載せない判断」)
  • ③ commit と push 状態: GitHub Pages はリポジトリの最新コミットを公開対象にする。push されていない変更は公開URLに反映されない
1限 後半 約50分

公開前のレイアウト微調整 → commit & push する

レイアウト微調整(30分)

  • 第3回で書いた CSS をそのまま公開できる状態にする最終調整
  • チェック観点:
    • 見出し(h1 / h2 / h3)と本文(p)のサイズバランス
    • 色は1〜2色に絞れているか(第3回の「自分らしい1色」ルール継続)
    • リンク(a)の色が本文と区別できるか
    • 余白(margin / padding)で読みやすい呼吸が入っているか
  • 1行ずつ書いて Simple Browser で確認を繰り返す。第3回と同じリズム

「載せる/載せない」を自分で決める(10分)

  • 本名は「公開してよい」と自分が判断できるか(クラスメイトの判断と違って当たり前)
  • 学校名・学年は載せるか、伏せるか
  • SNS アカウントを載せるなら公開アカウントのみ。鍵アカウントは載せない
  • 迷ったら載せないを選ぶ。後から追加はいつでもできる

commit & push(10分)

  • Codespaces の左側「ソース管理」(Source Control)タブで変更ファイル一覧を確認
  • コミットメッセージ例: 公開前の最終調整
  • 「Commit」→「Sync Changes」(または「Push」)で GitHub に反映
  • GitHub.com の自分のリポジトリページで最新コミットが反映されたか確認
「公開URLに恥ずかしいコミットを残さない」必要はない: Git の履歴は学習プロセスそのものです。「最初の一歩」のコミットも、レイアウトを直したコミットも全部残してOK。後で見返すと「自分はここから始めた」という記録になります。
休憩 10分
2限 前半 約50分

GitHub Pages を有効化して公開URLを取得する

リポジトリの Settings を開く(5分)

  • GitHub.com で自分のリポジトリのページを開く(https://github.com/<ユーザー名>/<リポジトリ名>)
  • 上部タブの「Settings」をクリック(自分が所有しているリポジトリでないと表示されない)
  • 左サイドバーの「Pages」を選択

Source の設定(10分)

  • 「Build and deployment」セクションの「Source」ドロップダウンで「Deploy from a branch」を選択
  • 下に出る「Branch」ドロップダウンで main を選択
  • 右隣のフォルダドロップダウンで / (root) を選択
  • 「Save」ボタンをクリック

デプロイ待ちと公開URL確認(25分)

  • Save 後、Pages 設定ページ上部に 「Your site is live at ...」 という案内が表示されるまで待つ
  • 公式: 反映まで最大10分(通常は1〜3分)。教室では待ち時間を使ってクラスメイトの進捗を確認するのもよい
  • リポジトリの「Actions」タブで pages build and deployment ワークフローの進行状況を見られる
  • 表示された公開URLをコピーしてブラウザの別タブで開く——自分の index.html が表示されることを確認

Public / Private と無料プランの注意(10分)

  • GitHub Pages の無料プランは public(誰でもコードを見られる)リポジトリのみ対応——本日の授業は public で進めるので、プランの違いを覚える必要はない
  • private リポジトリで Pages を使いたい場合は有料プランへのアップグレードが必要(GitHub Pro / Team / Enterprise などの上位プラン)。GitHub Student 認証済みなら Student Developer Pack の特典として GitHub Pro が無料で使える
  • 豆知識(2026年5月現在の表示状況): github.com/pricing の個人プランタブには Free / Team / Enterprise の3つのみが表示されていて、Pro が見当たらない状態(プラン構成の整理が進行中の表示)。Pro 自体は 公式 docs と Student Pack に今も残っているため、pricing ページで「Pro が無い」と気づいた人がいても焦らなくてOK
  • 注意: 2026-04-20 から Copilot Pro / Pro+ / Student の新規申請が一時停止中(既存認証済みユーザーは継続利用可)。再開時期は公式の Important 掲示で都度確認。Pages の利用自体は public リポジトリで全員可能
「Source」と「Branch」の用語は公式 UI の表記そのまま: GitHub の UI は英語が基準で、日本語化されていない要素も多くあります。「Source」「Branch」「Save」はUI のまま覚えるのが結局はやい。教える時も英語と日本語訳の両方を併用します。
2限 後半 約30分

公開URLを実機で確認しトラブルシューティング手順を身につける

スマホ実機で確認する(15分)

  • 公開URLを LINE などで自分宛にメッセージ送信、または手で打ち込んでスマホで開く(QR コード変換は Week 5 で扱う)
  • PC とスマホで見え方が違っていて当然——本格的なレスポンシブ対応は Week 5 のテーマ
  • 今日は「気になった点をスクリーンショットで保存」だけしておく。Week 5 の素材になる

表示されない時のチェックリスト(15分)

  • ① 「404 — Not Found」が出る → index.html がリポジトリのルート(一番上)にあるか確認。ファイル名のスペル(Index.html や index.htm はダメ)も確認
  • ② 古いまま変わらない → 反映に最大10分かかる。ブラウザの強制再読み込み(Mac: Cmd + Shift + R / Windows: Ctrl + Shift + R)でキャッシュをクリア
  • ③ CSS が反映されない → <link rel="stylesheet" href="style.css"> のスペル、style.css ファイルのスペル、大文字小文字を確認
  • ④ 画像が表示されない → 画像のパスと大文字小文字。GitHub Pages は Linux サーバー上で動くため、ファイルパスの大文字小文字を区別する(Codespaces のローカルプレビューや Windows / macOS の標準設定では同一視されるが、本番サーバーでは Profile.png と profile.png は別物として扱われる)
  • ⑤ それでも直らない → 講師に公開URLとスクリーンショットを見せて相談。エラーメッセージは「読む」が基本(第13回でも同じことを練習する)
まとめ 約10分

次回予告と今日の振り返り

  • 次回(第5回): レスポンシブ＆スマホ実機確認＆バグ修正ワーク①——今日取得した公開URLをQRコードに変換してスマホで読み取り、PC とスマホでの表示の違いをメディアクエリで吸収する。AI に「バグ入りスマホ対応 CSS」を生成させ、修正する演習も行う
  • 公開URLは必ず控えておく。スマホのブックマークや自分宛のメッセージに保存
  • 「公開URL」「Settings → Pages」「main / (root)」の3つを口に出して言えるか確認して退出

課題・次回までにやること

必須
公開URLを記録する

自分のメモアプリ・スマホのブックマーク・自分宛メッセージなど、次回必ず取り出せる場所に保存する。Week 5 で QR コード変換に使います。

必須
家のスマホで公開URLを開き、気になった点をスクリーンショットに残す

「文字が小さい」「画像がはみ出る」「余白が詰まりすぎ」など、PC では気にならなかったことがスマホで見えるはずです。今日は直さない、Week 5 の素材として記録するだけ。

推奨
家族や友人に公開URLを見せて反応をもらう

「世界に公開された自分の作品」を一人でも誰かに見せる体験。褒められたら次回シェア歓迎、辛口の指摘も Week 5 の素材になります。
